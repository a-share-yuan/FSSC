# 60 · 审批动作归属缺陷整改报告

> 触发：2026-09-17 用户反馈「我的单据 → 更多 → 竟然有『审批通过 / 驳回』，我自己填单还能自己审批？」
> 定位：这是一类**系统性 UI 缺陷**，非单点。全国人（申请人）视角与普通列表页普遍存在「不该出现的审批按钮」。

---

## 1. 缺陷本质（一句话）

**前端用「单据状态 = APPROVING」来决定是否显示「审批通过 / 驳回」按钮，完全不判断「这单是否轮到我审批」。**

后果有三类：

| 症状 | 业务上为何荒谬 |
|---|---|
| 申请人在「我的单据」看到自己单据的「审批通过 / 驳回」 | 自己审自己、自己退回给自己 |
| 任意有列表页权限的人看到全部在途单据的审批按钮 | 越权按钮，点了必报错 |
| `approve` 与 `reject` 绑到同一个处理函数且未传决策参数 | 点「通过」实际执行「驳回」 |

---

## 2. 后端是否也有越权？（先行排除）

**结论：后端无越权漏洞，是纯粹的「UI 把不该有的按钮放出来了」。**

证据（`fssc-server`）：

| 机制 | 位置 | 说明 |
|---|---|---|
| 越权守卫 | `WfEngineFacade` V1.3.19 | 非当前任务办理人调用完成接口 → 403 |
| 自审禁止开关 | `sys_config.approve.deny_self = '1'` | 已开启，**fail-closed**：禁止审批自己提交的单据 |
| 待办接口 | `WfTaskController#/tenant/wf/todo` | 已按 `assignee` / 候选角色过滤，只返回当前用户自己的待办 |

因此用户点击这些错误按钮，**必然**收到「禁止审批自己提交的单据」或 403 —— 纯属无效按钮，正是用户口中的"垃圾问题"。

### 4.1 核心口径统一

> **只有「当前登录用户在 `/tenant/wf/todo` 中存在该单据的待办任务」时，才允许在列表上直接审批。**

理由：待办接口本身已按 `assignee` / 候选角色过滤，它就是「是否轮到我」的**权威数据源**；与「我的待办」页面口径完全一致。

### 4.2 新增前端归属判定 composable

`fssc-web/src/composables/useApprovalScope.js`：

- 模块级缓存 + 单飞（inflight）复用 → 多页面共用同一份待办数据，不重复请求；
- 惰性加载 + TTL 20s 自动刷新 → 审批完成后按钮自动消失，页面**零改动**；
- 调用失败**降级为空集合** → 宁可少显示按钮，也**绝不显示错误按钮**；
- 输出：`canApprove(row)`（是否轮到我）、`taskIdOf(row)`（精确审批用）、`refresh()`。

用法：

```vue
<InlineActions :show-approve="canApprove(row)" :show-reject="canApprove(row)"
               @approve="handleApprove(row)" @reject="handleReject(row)" />
```
```js
import { useApprovalScope } from '../../composables/useApprovalScope'
const { canApprove, taskIdOf } = useApprovalScope()
await wfApi.approve({ taskId: taskIdOf(row), approved: true, comment: '审批通过' })
```

### 4.3 精确审批：按 taskId 而非猜 bizType

原先多处 `wfApi.approveByBill(guessBizType(), id, ...)` —— `guessBizType()` 是页面级常量猜测，易错。
改为 `wfApi.approve({ taskId: taskIdOf(row), ... })`：**taskId 来自我的待办，必然对应正确任务**，无需猜测。

### 4.4 三类页面分别处置

| 页面类型 | 处置 | 代表文件 |
|---|---|---|
| 申请人 / 个人视角（我的单据） | **移除**审批 / 驳回，仅保留 查看 / 追溯 / 撤回 / 作废 / 冲销（均为申请人自身动作） | `ExpenseBillListTab.vue`、`RequisitionWorkbench.vue`(我的单据 tab) |
| 流程驱动业务台账 | 审批按钮改为 `canApprove(row)` 门控 + 按 `taskId` 审批 | 12 个台账列表（见 §5） |
| 模块自有审批（非流程驱动） | **不能用待办门控**，改用该模块权限码门控 | `Contract.vue`（`contract:update`）、`ArchiveBoard.vue`（合规模块 `archive-access`） |

>  关键甄别：`Contract` / `ArchiveBoard` 的审批走的是**模块自己的接口**（`contractApi.approve` / `complianceApi.archiveAccess.approve`），不产生 `wf_task`，因此**不能**用「我的待办」门控，否则按钮会全部消失（误伤）。这两处改用权限码 + 状态双重门控。

## 7. 经验沉淀（可复用）

1. **按钮可见性必须与「可执行性」同源**：审批按钮的可见条件必须等于「当前用户确实能执行该动作」，而不是「单据处于某状态」。
2. **权威数据源优先**：能用「我的待办」这种已按人过滤的接口，就不要在前端自己拼归属判断。
3. **流程审批 ≠ 模块审批**：先确认审批是 `wf_task` 驱动还是模块自有接口，再决定门控方式（待办 vs 权限码），否则误伤。
4. **前端门控 + 后端 fail-closed 双保险**：即便前端漏判，后端也必须拒绝（本项目已有）。
5. **扫描器要能复扫清零**：一次性扫描没有价值，能反复运行且误报为 0 才是资产。
