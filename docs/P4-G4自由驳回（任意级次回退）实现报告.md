## 1. 复核结论（动手前的侦察，两处更正方案文档旧表）

### 1.1 「逐级驳回」名不副实 —— 驳回 = 作废重提

`WfEngineFacade.terminateAsRejected()`（:1584）实证：

```
驳回 → runtimeService.deleteProcessInstance(pinst, "审批驳回")
     → wf_instance 置 REJECTED
     → WfProcessEndedEvent(approved=false, rejectType)
```

即 **`rejectType`（THROW_BACK / GRADE_BY_GRADE）只是发给事件总线的标签，完全不改变流程走向**。
所有驳回路径（普通节点、票签未达阈值）最终都是"终止实例 + 单据置 REJECTED + 发起人重新提单"。
动态生成的 BPMN 根本没有 `${approved == false}` 的驳回分支（:2536 注释自己就承认了这一点）。

在审批内核上的最大单点差距。

### 1.2 G6「指定下一步处理人」方案文档低估 —— 早已完整实现

PICK 档（V1.4.0）已具备：`pick_assignee_{nodeKey}` 流程变量、灰度开关（fail-closed）、
候选集校验（点名对象必须在候选内）、`enforcePickOnApprove` / `enforcePickOnStart` 双入口、
提单页选人。**G6 无需开发**，仅需在方案文档更正状态。

## 2. 设计（与「已办撤销」同一套纪律）

| 纪律 | 落地 |
|---|---|
| **只读预览先行** | `GET /wf/reject-targets?taskId=` 纯查询，列出可退回节点 + 退回后将作废的后续节点 |
| **开关 fail-closed** | `sys_config.wf.reject.free.enabled` 缺省 0，读配置异常也按关（与 `wf.withdraw.done.enabled` 同口径） |
| **预览与执行同口径** | 候选集与 `withdrawPreview` 共用 `wfQueryService.chain` 的 DONE/REJECTED 节，**不另造第二套"哪些节点算上游"** —— 两处口径分叉比没有预览更糟 |
| **默认路径逐字不变** | 不选级次 / 开关未开 / 票签节点 ⇒ 走原 `terminateAsRejected`，对存量行为零影响 |
| **失败不降级** | 三道硬闸任何一道不过都抛业务异常；静默降级回"终止本流程"会让审批人以为退回成功、实际单据已作废 |

### 2.1 钩子位置（关键决策）

G4 分支放在 `complete()` 内、加签回跳钩子之后、`taskService.complete()` **之前**：

```
越权守卫 → deny_self → 连办拦截 → 加签回跳钩子 → 【G4 自由驳回钩子（提前 return）】
        → taskService.complete() → 票签 → 驳回兜底(terminateAsRejected) → 节点同步 → 抄送
```

理由：底部兜底是"先 complete 再 deleteProcessInstance"，执行已向前推进；若在 complete 之后
搬执行，就要从**推进后的新节点**往回搬，形成二次搬执行。提前 return 与文件里已有的加签回跳
范式完全一致。

### 2.2 三道硬闸（`rejectToNode`）

1. **目标节点必须属于本实例已完成节点**（取 `chain` 的 DONE/REJECTED 集合做白名单，防跨实例/未来节点乱搬）；
2. **实例在办任务必须恰好 1 条**（并联/会签时"搬执行"语义不唯一）；
3. **票签（VOTE）节点不支持**（按比例聚合裁决的节点，指定级次驳回会破坏计票语义）。

### 2.3 执行收尾（搬执行成功后）

| 步骤 | 说明 |
|---|---|
| `moveActivityIdTo(fromNodeKey, targetNodeKey)` | Flowable 8「搬执行」原语，目标节点的任务由引擎重建 |
| `markTaskDone(旧taskId)` | 待办镜像置 DONE + 回写真实操作人 |
| `writeHistory(REJECT_TO / REJECT_TO_DONE)` | 搬执行**前**先写一条（失败可追溯），成功后再写终态；意见带 `[驳回至 nodeKey]` |
| `syncInstanceAfterAdvance` | 复用既有推进收口：三级取人重算新任务指派（含 PENDING 镜像补账）+ 刷新实例视图 |
| `notifyUser(新任务办理人)` | 站内信"单据被退回至你办理"；收尾各步独立 try/catch，**绝不因收尾失败掩盖搬执行已成功** |


FSSC 各流程首节点即"提交申请/提交报账单"（动态指派 assignee=${approver}）。
驳回到首节点后，发起人在**原单、原实例、原单号**上改完重新提交，流程增量续走 ——
不需要任何单据状态机改造，审批历史完整保留。

## 5. 重启窗口验证清单（开关开启前必须全绿）

1. 造 4 节点测试流程：提交 → A 审 → B 审 → C 审，走至 C。
2. `GET /wf/reject-targets?taskId=<C的任务>`：返回 enabled=false（开关未开）+ 候选集（A、B、首节点）。
3. **开关关闭回归**：C 驳回（不选级次）⇒ 实例终止、单据 REJECTED（与现状逐字一致）。
4. 置 `sys_config: wf.reject.free.enabled=1`，重查 reject-targets ⇒ enabled=true。
5. C 驳回选"退回到 A" ⇒ A 的待办重新出现；`wf_task_history` 有 REJECT_TO + REJECT_TO_DONE 两条；A 办理人收到站内信。
6. A 通过后 B、C 重新依次出现（**增量续走**，非重开实例）；`wf_instance.current_node/current_assignee` 正确。
7. 驳回到首节点 ⇒ 发起人原单改完重提，单号不变、审批历史含全部旧节点。
8. 会签/并联在办时执行驳回选级次 ⇒ 明确报错"不支持指定级次驳回"，流程无变动。
9. 票签节点 ⇒ reject-targets enabled=false（voteNode=true）。
10. 搬执行失败注入（目标节点 key 改成未完成节点）⇒ 报错且流程无变动、`wf_task_history` 有 REJECT_TO 试探痕。
11. 前端：开关关 ⇒ 级次下拉不渲染；开 ⇒ 选中级次后黄条明示将作废的节点清单。
12. `reject-targets` 对 30+ 处审批弹窗复用点零影响（默认不请求，仅驳回态发一次 silent GET）。
