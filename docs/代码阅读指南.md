# 怎么读懂一个你不了解的项目（尤其是规模较大的存量项目）

> 这份文档不是 FSSC 的功能说明，而是**方法**。它记录了我们自己面对这个 131,428 行 Java + 56,674 行 Vue 的代码库时，实际奏效的读法、踩过的判断错误，以及每一条结论应该拿什么证据来支撑。
> 面向对象：① 第一次接手这个仓库的贡献者；② 任何"代码不是我写的、我需要一个下午搞懂它"的人。

## 0. 先接受三个前提

1. **代码不会告诉你它是否真的在跑。** 一个方法存在、写得很完整、甚至带注释，都不代表它被调用过。这个项目里确实存在"配置读进来了但没人用"的键（见第 4 节）。
2. **注释可能是编造的。** 本项目源码里存在大量"引用了不存在的表名/字段名/类名"的说明性注释，也有注释声称的行为与代码相反。**注释只能当线索，不能当证据。**
3. **工作目录里有一大半不是活的。** 同一份 BPMN 有 4 份副本、构建产物目录有 6 份锁文件残留、还有一个空壳 `src/` 不参与构建。判断"哪份是真的"要先于读代码。

## 1. 顺序：地图 → 数据 → 一条链 → 再谈理解

不要按文件名字母序读，也不要从 `Controller` 开始逐个读。有效的顺序是这四步：

```
① 目录地图（30 分钟）    ② 数据模型（2 小时，最划算）    ③ 垂直切一条链（半天）    ④ 横向机制（按需）
   谁负责什么                表 + 状态列 + 外键              一个真实动作走到底            鉴权/租户/事务/调度
```

**为什么数据模型先行**：表结构是这个系统唯一没法骗你的东西。类名可以改、注释可以错、配置可以不生效，但单据状态能不能从 `DRAFT` 走到 `APPROVING`，取决于有没有人真的 `UPDATE` 那一列。看懂 243 张表里的 20 张核心表，你就理解了 80% 的业务；反过来读 1,007 个类不一定会懂"核销"是什么。

- 地图：[`模块地图.md`](模块地图.md)（33 个域，文件/行/端点/表数量全实测）
- 数据：[`数据模型.md`](数据模型.md)（含"三台状态机"与列名真值表）

## 2. "追踪弹"：一条链读到底，胜过十个文件读一半

选一个**你在界面上能亲手做出来的动作**，把它从 HTTP 入口跟到数据库落列。判断"我是不是真的读懂了"的标准很硬：**你能说出这条链上每一步改了哪张表的哪一列**。

本项目的一条真实追踪弹——「提交一张报销单」，逐跳都是实测行号：

| # | 位置 | 干了什么 | 你能验证的现象 |
|---|---|---|---|
| 1 | `fssc-start/src/main/java/com/fssc/expense/controller/ExpenseBillController.java:46` | `@PostMapping("/submit/{id}")`，接 `approverUserId` / `firstAssigneeUserId` 两个可选参数 | F12 看到 `POST /api/tenant/expense/bill/submit/123` |
| 2 | 同文件 `:47` | 转手给 `expenseBillService.submit(...)`——Controller 里没有任何逻辑 | 想改行为不用动 Controller |
| 3 | `expense/service/ExpenseBillService.java:642` | **状态闸**：非 `DRAFT` 直接抛业务异常 | 连点两次提交，第二次报错 |
| 4 | 同文件 `:656~657` | **CAS 更新**：条件带上 `status='DRAFT'` 才把它置成 `APPROVING` | 并发双击不会产生两个流程实例 |
| 5 | 同文件 `:664`、`:669` | 明细至少一条 + `validateAmountReconcile`（头金额=明细合计） | 删光明细后提交被拦 |
| 6 | 同文件 `:675` | `precheckService.failures(billId)` —— **合规预检在这里拦**，不在引擎里 | 违反费用标准时报"提交被拦截（N 项不合规）" |
| 7 | 同文件 `:685` | `fraudDetectionService.checkAndBlock(...)` 反舞弊拦截 | — |
| 8 | 同文件 `:757~759` | 若费用项要求发票（`need_invoice=1`），数 `exp_bill_attach` 里 `INVOICE` 附件条数 | 不传发票就提交会失败 |
| 9 | 同文件 `:876` | `wfEngineFacade.start(bizType, billId, approver, title, total, ...)` —— **流程实例在这一刻才创建** | `wf_*` 台账出现新实例 |
| 10 | `workflow/service/WfEngineFacade.java:443/447/451/456/510` | `start()` 的五个重载，最终落到 Flowable 的 `RuntimeService` | `ACT_RU_*` 出现运行时数据 |

**这条弹打完，你顺手就回答了一堆问题**：状态机谁负责？（业务 Service，不是引擎）合规在哪拦？（提交时，不是审批时）并发怎么防？（SQL 条件更新，不是分布式锁）为什么驳回重提会生成新实例？（`start` 只创建，不复活）

 关键心态：**中途不要跳去"顺便看看别的"**。看到 `PrecheckService` 好奇就先记进清单，继续走完当前这条链，回来再打第二发。

### 自己选一条链的模板

```
界面入口 → Network 面板里的第一个请求（记下 method + path）
  → grep 这个 path 找到 @RequestMapping 前缀 + @PostMapping 方法
  → 进 Service，只看这个方法和它直接调的 3~5 个方法
  → 每次看到 mapper.update*/insert* 就把「表.列」记下来
  → 走到引擎或事件监听（本项目是 ExpenseWfEventListener 这类）为止
```

## 3. 判断"哪份代码是活的"：五种死件与它们的识别法

这个仓库里已经确认存在的误导源，以及对应的判据：

| 现象 | 具体位置 | 判据 |
|---|---|---|
| **空壳目录** | `fssc/fssc-server/src/`（父 pom 是 `packaging=pom`，只有 `fssc-common` 与 `fssc-start` 两个 module） | 以 `pom.xml` 的 `<modules>` 为准，不看目录是否存在 |
| **多份副本** | `bpmn-repo` 在工作区根（2,790 文件）／`fssc/bpmn-repo`（14）／`fssc/fssc-server/bpmn-repo`（32）／`fssc-start/src/main/resources/processes`（2） | 真相源＝配置项 `fssc.wf.bpmn-repo-dir` 指向的那份；其余是历史遗留 |
| **构建产物当源码** | `fssc-common/target_locked6 … target_locked11/`（6 份、含 5 个 jar + 70 个 `.class`）、`fssc-web/dist32…dist38 / dist_h5 / dist_check_*`（9 个） | 只从 `src/` 读；`.class`/`.jar`/`dist*` 一律排除 |
| **临时件躺在源码树** | `fssc-start/src/main/java/com/fssc/_tmp_s3_treasury.log` | 文件名前缀 `_` / `.tmp` / `temp_` 出现即疑 |
| **过时说明** | `application.yml` 的 `info.app.java: 17`（实际编译目标是 26） | 版本事实只认 `pom.xml` 与 `mvn -v`，不认描述性字段 |

**通用技巧**：想知道某个类是不是"活的"，别看它写得多好，看**有没有人引用它**。IDE 的 Find Usages / `grep -rn "类名" src/main/java | grep -v "该文件本身"`，零引用即可判死件（还要排除反射与 Spring 扫描）。

## 4. 伪配置识别：这个项目最伤信任的地方

这类大型代码库的典型形态是：**先把配置项写进 yml/DTO/设计器属性，再"将来某天"接线**。而这个"将来"往往永不到来。识别方法（每条都能在 5 分钟内做完）：

1. 拿到键名（例如 `wf.model.xxx`、`exp.loan.max`）。
2. 全 `src/main/java` grep 这个**字面量**。命中只在 `@ConfigurationProperties`/`@Value` 一侧 → 读进来了。
3. 再看这个字段/属性**被读取的位置**有没有出现在任何 `if` / 计算 / SQL 条件里。只有赋值没有消费 ⇒ **伪配置**，写了也不生效。
4. 拿不准就用**运行时反证**：把它改成明显荒谬的值（0、-1、不存在的枚举），重启，跑一次相关操作。**行为没变就是没接线。**

本项目里已经用这套方法确认过的例子，写在 [`流程引擎技术说明.md`](流程引擎技术说明.md)（节点属性层若干项标为"仅登记未接线"）与 [`架构总览.md`](架构总览.md) §4。 反证法要**在演示环境做，绝不碰生产库**，而且记住：**管理员账号不参与提单/审批**（见 [`演示账号.md`](演示账号.md) 的分工铁律）。

对外文档里怎么写伪配置？——**照实写"当前不生效"**，并给出你的核查位置。这比含糊其辞专业得多，也省掉后来者两小时。

## 5. 状态机：三个"状态"列极易混淆

财务系统里"状态"这个词至少有四五个含义。改代码前先确认你说的是哪一个：

- **单据状态**：业务表自己的 `status`（`exp_bill.status`：DRAFT/APPROVING/…），由业务 Service 改。
- **审批节点状态**：`wf_approval_item` 之类的留痕表，由引擎侧改。
- **流程实例状态**：Flowable `ACT_RU_/ACT_HI_` 里的运行时/历史，由引擎内部改。
- **凭证状态**：`DRAFT`/`POSTED` 之类，制证与过账分开。

 本项目的实测坑：**引擎侧终结 ≠ 业务侧终结**。审批流被作废/终止时，如果业务 `status` 没被同步回写，单据会滞留在中间态（表现为"按钮一直挂着但点什么都报错"）。凡是看到 `CANCELLED`/`VOID` 之类的分支，**必查它有没有同时写业务表**——这一条是判断"这个流程功能是不是真的做完了"的分水岭。

另一个坑：**同一个 `status` 列在不同表里语义相反，而且是实测的**。`framework/log/OperLogAspect.java:106` 给平台侧 `pf_oper_log` 写的是 `status = ok ? 1 : 0`（**1＝成功**），而 `:123` 给租户侧 `sys_oper_log` 写的是 `status = ok ? 0 : 1`（**1＝失败**）。写查询 SQL 或做报表前先确认你面对的是哪张表——按直觉猜会得出完全相反的结论。

## 6. 用交付物反过来验证理解：三个"我是不是看懂了"的测试

- **测试 A（数据）**：不看代码，口述"一张报销单从提交到归档要动哪 8 张表"。说不出来 ⇒ 你还没读懂数据模型，回去画 ER 图。
- **测试 B（界面）**：随便点一个按钮，说出它打的是哪个 URL、哪个方法。打不出来 ⇒ 你对 API 前缀约定还不熟（`/api/tenant/**` 是租户端，`/api/platform/**` 是平台端，`/api/ai/**` 是 AI 网关；见 [`模块地图.md`](模块地图.md)）。
- **测试 C（改动）**：给自己出一个"最小改动"任务——例如"让某个部门的报销必须附发票"。如果你只能靠改代码，说明你还没找到配置/主数据的入口；本项目这类规则在费用项主数据（`need_invoice` 列）与合规规则里。

## 8. 维护者请保持这份方法有效

如果这个项目要长期开源，读码方法本身也要维护：

1. 任何"某配置项不生效"的新结论，**必须附带你的 grep/反证位置**，并写进对应域文档，不要只留在聊天记录里。
2. 新增域或大重构后，重跑 `node _tools/inventory.mjs` 与 `node _tools/payload.mjs`，让地图数字跟着代码变。
3. 巨型文件（[`模块地图.md`](模块地图.md) 列了前几名，最大单类 6,359 行）要**持续标注"别通读、按方法名查"**，并作为拆分候选记进 [`docs/adr/`](adr/)。
4. 文档里的每一个数字都应是**实测**得来的。本项目所有文档遵循这条规则，做不到时会显式写"尚未验证"——请你也这样。
