# 部署运维

## 1. 三种部署形态

### 形态 A0：源码调试（开发用，不起 jar）
```bash
cd fssc/fssc-server/fssc-start
mvn spring-boot:run \
  -Dspring-boot.run.arguments="--spring.config.import=optional:file:../../../../.env"
```
前置：MySQL 8（fssc + fssc_image 两库）+ Node 24（前端另起）。
`fssc-server` 是父工程（`packaging=pom`），`spring-boot:run` 必须在 **`fssc-start`** 目录跑；
主类 `com.fssc.FsscApplication`，IDE 里直接 Run 即可断点调试。
`.env` 不会自动生效（本仓无 dotenv 加载器），靠上面的 `--spring.config.import` 读入。

### 形态 A：jar 直跑（开发/小规模）
```bash
cd fssc/fssc-server && mvn -q clean package -DskipTests
set -a && . ../../.env && set +a      # 把 .env 导出为环境变量
java -jar fssc-start/target/fssc-server.jar
```
前置：MySQL 8（fssc + fssc_image 两库）+ Node 24（前端另起）。

### 形态 B：Docker（推荐单机演示）
```bash
cd fssc/docker
docker build -t fssc:latest -f Dockerfile ..
docker run -d --name fssc -p 8089:8089 \
  -e FSSC_DB_PASSWORD=xxx -e FSSC_JWT_SECRET=xxx \
  -e FSSC_DB_MASTER_URL='jdbc:mysql://<db-host>:3306/fssc?...' \
  fssc:latest
```
镜像是多阶段构建（Maven 构建 → JRE 运行），前端产物需另行构建或挂 nginx。

### 形态 C：Kubernetes（生产）
`fssc/docker/k8s-fssc.yaml` 提供编排样例：Deployment + Service + 探针。
- **多实例必需**：`FSSC_REDIS_ENABLED=true`（分布式状态）+ 所有实例同一
  `FSSC_JWT_SECRET`（否则表现为"刚登录就被踢"）；
- 调度锁在单机模式下用 MySQL GET_LOCK，多实例必须 Redis。

## 2. 配置项全表（.env）

| 变量 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `FSSC_DB_PASSWORD` | 是 | 无（fail-fast） | 两库共用口令 |
| `FSSC_JWT_SECRET` | 是 | 无（fail-fast） | ≥32 字节；多实例必须同值 |
| `SPRING_PROFILES_ACTIVE` | | dev | prod 关闭 SQL 日志 |
| `FSSC_DB_MASTER_URL` / `FSSC_DB_IMAGE_URL` | | 127.0.0.1:3306 | 跨机部署才改 |
| `FSSC_DB_USERNAME` | | root | |
| `SERVER_PORT` | | 8089 | |
| `FSSC_API_TARGET` | | http://127.0.0.1:8089 | 前端 preview 反代目标 |
| `FSSC_REDIS_ENABLED` | | false | 多实例必须 true |
| `FSSC_OCR_CHANNEL` | | mock | mock/gateway/paddle/http |
| `INVOICE_GATEWAY_*` | | — | 发票网关（默认 8096） |
| `FSSC_BANK_GATEWAY` | | mock | 银企通道 |
| `FSSC_BPMN_REPO_DIR` | | ./bpmn-repo | 流程模型 git 工作副本 |

**铁律：口令/密钥类无默认值，留空启动失败是有意的**；生产凭据禁入库、禁进镜像层。

## 3. 健康检查与监控

- 存活/就绪探针：`/actuator/health/liveness`、`/actuator/health/readiness`
  （免鉴权，给 k8s 探针用）；
- 优雅停机：`server.shutdown=graceful`（30s 窗口）；
- 日志：`fssc/fssc-server/logs/`（按日切割，**不入库不进镜像**）；
- 关键业务监控抓手：`op_sla_breach`（SLA 违约）、`op_stability_log`（卡单率）、
  `wf_task` 停留时长（节点卡点）、`pf_oper_log`（操作审计）。

## 4. 备份策略

| 对象 | 方式 | 频率建议 |
|---|---|---|
| 主库 `fssc` | mysqldump --single-transaction（含 routines/triggers/events） | 每日 + 变更前 |
| 影像库 `fssc_image` | 同上（数据增长快，可只备结构 + 近期数据） | 每日 |
| 影像文件 | `fssc/fssc-server/data/files/` 目录同步 | 实时/每日 |
| 流程模型 | `bpmn-repo/` 是 git 工作副本，天然有版本 | 持续 |
| 配置 | `.env`（不进库！进密钥管理系统） | — |

恢复演练每季度至少一次：备份 → 空库导入 → 起服务 → 抽查关键单据。

## 5. 升级流程

1. 停服务（先停看门狗/守护进程，再停后端，`netstat` 复核端口）；
2. 备份两库；
3. 结构变更：改完在演练库上重导一份整库 dump 覆盖 `db/Dump<日期>/` 并同步 `db/README.md` 的日期（**每步留执行记录**）；
4. 替换 jar（**先移走旧 jar 再打新包**，否则 maven 判"jar 比 classes 新"跳过重建，
   打出假新包）；
5. 起服务 → 健康检查 → 冒烟（登录/提单/审批/凭证）；
6. 挂回看门狗。

**校验新包的唯一标准是 zip 内 class 时间戳与新增端点字符串**，不看 jar 大小/mtime。

## 6. 常见运维事故与对策

| 事故 | 根因 | 对策 |
|---|---|---|
| 重启后新端点 404 | 用了旧 jar | 按 §5 第 4 步校验 class |
| 服务被静默杀死 | 无看门狗 | 挂看门狗 + 就绪探针 |
| "刚登录就被踢" | 多实例 JWT_SECRET 不一致 | 统一注入 |
| 归档失败 | 冷热表列序不一致 | 加列同步冷表后重跑 |
| 配置改了不生效 | node_key 是孤儿行 | 对照已部署 BPMN 核对 |
