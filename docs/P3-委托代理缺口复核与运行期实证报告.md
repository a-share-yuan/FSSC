## 0. 结论速览

方案 §1.4 列了 4 项残留缺口。逐项复核后，**其中 3 项是真实缺口、1 项经实证并非委托特有缺口**：

| # | 方案原文的缺口 | 复核结论 | 证据 |
|---|---|---|---|
| 1 | 委托到期**自动回收** |  **半成立**：功能上到期即失效（查询层按时间过滤），但 `status` 列**永无写入点** ⇒ 展示/审计口径与真实生效面不符 | 代码 + 审计数据（3 行中 0 行被回收） |
| 2 | 跨公司委托**约束** |  **成立**：`create()` 完全无公司维度校验，实测跨公司委托**被接受且能真正执行** | 运行期实证 A + C |
| 3 | 禁止自审**延伸**（受托人==发起人） |  **不是委托特有缺口**：`deny_self` 判定不含"是否委托"分支；旧问题另有其因（bizType 映射盲区） | 代码 + 运行期实证 C |
| 4 | 委托**完成回执**通知 |  **成立**：完全没有 | 代码 |

**本轮交付**：新增跨公司边界闸（默认拒绝 + 白名单）、新增 `WfDelegateExpireJob`、新增委托完成回执；前端补齐状态口径。后端 `mvn -o compile` **RC=0**、前端 `vite build` **通过**。

## 2. 运行期实证（不重启，打的是既有 8089）

### 实证 A：跨公司委托是否被接受 ——  缺口成立

| 项 | 值 |
|---|---|
| 动作 | 3818 陈修利（**company 33 昆山**）→ 3797 付程鹏（**company 1 集团**） |
| 接口 | `POST /api/tenant/wf/config/delegate/create`（用 3818 本人 token，满足 V1.3.19 的 fromUserId 校验） |
| 结果 | **HTTP 200** `{"code":0,"data":7,"msg":"成功","success":true}` |

### 实证 B1：无权第三人尝试审批 ——  越权守卫正确

| 项 | 值 |
|---|---|
| 动作 | 3805 刘志强（company 1，**非** `FSSC_AUDITOR` 成员、无委托）审批 3797 的任务 |
| 结果 | `{"code":403,"msg":"无权限访问：非当前节点办理人/候选人，无权办理此任务"}` |

### 实证 B2：U9 规则③④ 运行期生效（正向证据）

| 规则 | 构造 | 结果 |
|---|---|---|
| ④ 禁止循环委托 | 先有 `3818→3797`（A 的遗留），再建 `3797→3818`（同区间） | **被拒**：「对方已把待办委托给你，互相委托会形成回环」 |
| ③ 同期只能委托一人 | 已有 `3797→3818`，再建 `3797→3819`（同区间） | **被拒**：「该时间段你已有一条生效中的委托（同一时间只能委托给一个人）」 |

> 规则④的首次命中是**意外获得**的（v1 脚本未清理 A 的委托行），v2 起改为主动构造验证。

### 实证 C：受托人代办通道 ——  放行，且跨公司落地执行

| 项 | 值 |
|---|---|
| 构造 | 3797（company 1，任务当前办理人）委托 → 3819 胡培光（**company 32**）；再把 `wf_instance.start_user_id` 置为 3819（即"单据提交人"= 受托人） |
| 动作 | 3819 用**本人 token** 调 `POST /api/tenant/wf/approve` |
| 结果 | **HTTP 200 成功**；`wf_task.status=DONE`、`wf_instance.status=APPROVED` |
| 留痕 | `wf_task_history`：`APPROVE / oper_user_id=3819 / P3-C受托人代办` |

**两条结论**：

1. **委托通道有效** —— `NodeOrgResolver.canOperate` 第 3 条（受托人代办委托人待办）运行期确实放行。
2.  **跨公司委托真的能执行到底** —— 留痕的操作人是 **3819（company 32）**，而该流程所在公司是 1。
   即"外公司的人出现在本公司单据的审批留痕上"，这正是 §1.4-2 要防的内控可见性问题。

**关于 §1.4-3（自审延伸）为何判为"非委托特有"**：

```
complete() 的自审判定（WfEngineFacade:2422-2433）：
  if (isDenySelfEnabled())
      if (operator.equals(self.getStartUserId())
              && operator.equals(nodeOrgResolver.resolveApplyUserId(procInstId)))
          if (doneTasks > 0) throw "禁止审批自己提交的单据";
```

判定只涉及 `operator` / `startUserId` / `resolveApplyUserId` / 已完成任务数 —— **没有任何"是否通过委托获得资格"的分支**。
受托人拿到的只是"能调用 complete() 的资格"，进去之后面对的守卫与本人办理**完全一样**。
实证 C 之所以放行，是因为 `P2_TO` 未在 `BillRouteRegistry` 注册 ⇒ `resolveApplyUserId` 恒 `null` ⇒ 判定第二半恒假。
**根因归属：`deny_self` 的 bizType 映射盲区（与 D-FAM3-02「GL 域各表无 apply_user_id 列」同型），不是委托引入的新通道。**

## 3. 代码改动（改动前 / 改动后）

### 3.1 跨公司边界闸 —— `WfDelegateService.create()`

| | 改动前 | 改动后 |
|---|---|---|
| 校验规则 | ① 不能委托自己 ② 受托人可用 ③ 同期唯一 ④ 禁止循环 | 上述 4 条 **+ ⑤ 公司维度边界** |
| 跨公司行为 | 静默放行 | **默认 fail-closed 拒绝**；命中 `sys_config.delegate.cross_company.whitelist` 才放行（记 warn） |
| 无公司维度（`company_id=null`） | — | 放行但记日志：与 `canOperate` 的既有 null 放宽口径**保持一致**，避免误伤集团级账号 |
| 白名单格式 | — | 逗号分隔 `委托方公司>受托方公司`，两侧支持 `*`（`33>1`、`*>1`、`33>*`）；**未配置＝全禁** |
| 拒绝时的提示 | — | 明确写出双方公司号 + 配置键名，用户/管理员可自助定位 |

新增：`assertCompanyBoundary()` / `crossCompanyAllowed()` / `companyOf()`，注入 `ConfigService`（实时读配置，**改白名单无需重启**）。

### 3.2 到期自动回收 —— 新增 `WfDelegateExpireJob`

| | 改动前 | 改动后 |
|---|---|---|
| `status=EXPIRED` 写入点 | **无**（只有 NORMAL / DISABLED） | 每 10 分钟把 `NORMAL 且 end_time < now` 置 `EXPIRED` |
| 前端展示 | `MyDelegate.vue` 已写好 `EXPIRED→「已过期」` 分支，但**永远触发不到** | 分支真正可达 |
| 并发安全 | — | 条件更新（`WHERE status='NORMAL'`）：用户刚取消的行不会被覆盖成 EXPIRED |
| 引擎影响 | — | **不碰** Flowable、不改派任何任务；已落在受托人名下的待办不受影响 |
| 用户打扰 | — | **不发通知**（到期是建立委托时就选定的预期语义，逐条推送只会制造噪音） |

> 设计要点：功能上"到期即失效"**本来就成立**（生效判定走时间区间，不看 status）。本 Job 修正的是
> **口径与展示**，不是功能。这一点必须说清楚，否则会误以为"之前过期委托还在生效"。

### 3.3 委托完成回执 —— `WfEngineFacade.notifyDelegatePrincipal()`

| | 改动前 | 改动后 |
|---|---|---|
| 受托人办完后 | 委托人**无从得知**是"受托人办了"还是"流程卡住了"（任务已从自己待办消失） | 站内信回执：「你委托的待办已由 付程鹏(Y000185) 代办完成：<单据标题>」 |
| 判定口径 | — | 与 `canOperate` 第 3 条**同源**（toUserId=操作人、NORMAL、当前时间在区间内） |
| 风险控制 | — | 整体 try/catch **绝不阻断审批主链路**；逐条 catch 单发失败不影响其他收件人 |
| 失败不影响主流程 | — | 取展示名失败也降级回执本身仍发 |

### 3.4 前端状态口径 —— `MyDelegate.vue`

| | 改动前 | 改动后 |
|---|---|---|
| 状态列 | 三态：`NORMAL→启用` / `EXPIRED→已过期` / 其他→停用 | 五态：**生效中 / 待生效 / 已过期 / 已停用**（按时间就地计算，不依赖 Job 的 10 分钟窗口） |
| 取消按钮 | `NORMAL` 即显示 | 仅 `NORMAL` 显示（已过期/已停用再点只会拿到 4xx） |
| 新增弹窗 | 无任何边界提示 | 明确提示"只能委托同公司同事"，并给出白名单配置键 |

## 4. 影响面与风险评估

| 项 | 评估 |
|---|---|
| 跨公司闸对存量的影响 | **零**：只作用于 `create()` 新请求；存量 3 行跨公司委托不动（均为 DISABLED）。如需保留，配白名单即可 |
| 同公司委托 | **不受影响**（走 `Objects.equals` 直接放行） |
| 是否有真实业务被误伤 | 现网 5 家公司、委托功能此前**从未真实使用**（3 行全是测试数据）⇒ 无在用流程被打断；集团代子公司审批这类正当需求用白名单显式放行 |
| `WfDelegateExpireJob` 的写库量 | 过期行每次只写一次状态（条件更新），之后 `WHERE status='NORMAL'` 不再命中 ⇒ 稳态下**零写入** |
| 回执通知量 | 与"实际发生的受托代办次数"同阶（委托本身是低频自助动作），非通知风暴 |
