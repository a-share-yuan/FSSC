# 分库路由与服务拆分

一句话：**这是一个模块化单体**。同一枚 `fssc-server.jar` 既能在一个进程里跑全部业务，也能按域拆成几个独立进程；数据层先用"路由键"把每张表属于谁声明清楚，**物理切库和切进程都是可选项，不是既成事实**。

这份文档回答三个问题：哪些东西**已经**分开了、哪些只是**就位待开**、真要拆的时候还缺什么。

---

## 1. 数据层：五枚路由键，两枚已建池

对外只有一个 `@Primary` 路由数据源（`FsscRoutingDataSource`），Spring Boot 的 `DataSourceAutoConfiguration` 因它一声明 bean 就退避。

| 路由键 | 连接池 bean | 建池条件 | 未建池时 | 用途 |
|---|---|---|---|---|
| `master` | `masterDataSource` | 恒建 | — | 业务表、平台表、Flowable 引擎表 |
| `image` | `imageDataSource` | 恒建 | — | 影像域 6 张表，独立库 `fssc_image` |
| `replica` | `replicaDataSource` | `fssc.datasource.replica.enabled=true` | 别名 `master`，**仍套只读守卫** | 报表与追溯类只读读流量 |
| `document` | `documentDataSource` | `fssc.datasource.document.enabled=true` | 别名 `master` | 会计档案域 |
| `invoice` | `invoiceDataSource` | `fssc.datasource.invoice.enabled=true` | 别名 `master` | 发票与勾稽域 |

出处：`fssc/fssc-server/fssc-start/src/main/java/com/fssc/framework/config/DataSourceConfig.java:52`（master）、`:58`（image）、`:65`（replica 的建池条件）、`:73`（document）、`:81`（invoice）、`:94`（路由表装配）、`:114`（`setLenientFallback(false)`）。

**当前真实形态**：只有 `master` 与 `image` 两枚物理库。`document`／`invoice` 是**归属声明已就位、物理库还没切**——代码已经按域标注，切库时只改配置不改业务代码；`replica` 同理，且它**无论有没有独立副本都套 `ReadOnlyGuardDataSource`**，也就是说走 `replica` 的语句先被证明"只读"再执行（`:99`）。

>  别把"路由键存在"读成"已经分库"。`document`／`invoice` 现在指向的就是 `master`，库里查不到第二套档案表。

## 2. 路由怎么生效，以及三条写法约定

- 注解 `@FsscDataSource("image")`（`fssc/fssc-server/fssc-start/src/main/java/com/fssc/framework/datasource/FsscDataSource.java`）由 `DataSourceAspect.java` 拦截，键压进 `DataSourceContextHolder.java` 的 `ThreadLocal`，`FsscRoutingDataSource.java` 按键取池。
- **未知键直接抛异常**，不静默回落主库（`DataSourceConfig.java:114`）。这条是刻意的：静默回落会让"影像写进主库"这类事故看起来一切正常。
- 类级标注＝这个类默认属于哪个域；跨域读取用**方法级** `@FsscDataSource("master")` 覆写。全仓类级标注的分布：`image` 8 个文件、`document` 13 个、`invoice` 8 个、`replica` 5 个、方法级回读 `master` 19 个。
- **跨库取号只有一种正确写法**：挂起外层事务、绑主库连接、独立提交——见 `fssc/fssc-server/fssc-start/src/main/java/com/fssc/system/service/NumberRuleService.java` 的 `next(...)`（`master` + `REQUIRES_NEW`）。单据编号来自 `master` 的号段表，任何域都不许在自己库里造号。
- 需要读别的库又不能被外层事务绑住时，方法级叠 `NOT_SUPPORTED, readOnly=true` 挂起外层事务（例：`fssc/fssc-server/fssc-start/src/main/java/com/fssc/image/channel/HttpOcrChannel.java` 的 `recognize`）。

## 3. 进程层：四枚可独立启动的单元，共用同一枚 jar

拆分不靠多份构建产物，靠**换启动类＋换 profile**：

```
java -Dloader.main=com.fssc.image.ImageServiceApplication \
     -cp /app/fssc-start.jar org.springframework.boot.loader.launch.PropertiesLauncher \
     --spring.profiles.active=image,prod
```

| 单元 | 启动类 | profile | 端口 | 扫哪些包 | 清单 |
|---|---|---|---|---|---|
| 主服务 | `com.fssc.FsscApplication` | `prod` | 8089 | 全部业务域 | `fssc/docker/k8s-fssc.yaml` |
| 影像 | `com.fssc.image.ImageServiceApplication` | `image,prod` | 8090 | `image` + `framework` + `common` | `fssc/docker/k8s-image.yaml:57` |
| AI | `com.fssc.ai.AiServiceApplication` | `ai,prod` | 8092 | `ai` + `connector` + `framework` + `common` + `system.gateway` | `fssc/docker/k8s-ai.yaml:45` |
| 网关 | `com.fssc.gateway.GatewayServiceApplication` | `gateway,prod` | 8093 | `openapi` + `bcp` + `connector` + `gateway` + `framework` + `common` | `fssc/docker/k8s-gateway.yaml:48` |
| 报表 | `com.fssc.report.ReportServiceApplication` | `report,prod` | 8094 | `report` + `tracing` + `framework` + `common` | `fssc/docker/k8s-report.yaml:46` |

每台机器只跑自己那份 `@MapperScan` 覆盖到的 mapper，其余域根本不进容器——这就是"按域拆"的落点。报表单元额外置 `FSSC_REPLICA_ENABLED=true`（`fssc/docker/k8s-report.yaml:55`），把读流量真正引到 `replica` 路由键上。

拆出去的进程**仍然要连主库**：影像进程要取号、读字典，AI 进程要回读业务单，所以清单里 `FSSC_DB_MASTER_JDBC_URL` 与 `FSSC_DB_IMAGE_JDBC_URL` 同时给。跨进程调用走 HTTP，回主服务的地址由 `FSSC_BUSINESS_BASE_URL` 指定（`fssc/docker/k8s-ai.yaml:54`）。

## 4. 门面：跨域读写只有一条路

`document`／`invoice` 两域对外只通过 `framework/facade` 下的接口交互，域内实现类各自挂自己的路由键：

| 接口 | 实现 | 说明 |
|---|---|---|
| `ArchiveFacade` | `document/facade/ArchiveFacadeImpl` | 档案借阅／归还／销毁／完整性对账的对外出口 |
| `InvoiceFacade` | `invoice/facade/InvoiceFacadeImpl` | 只承诺"入池"两件事，影像进程可以用占位实现顶上去 |
| `InvoiceDomainFacade` | 同一实现类 | 发票＋勾稽表的跨域读写全集 |

拆成两个接口而不是一个，是为了让**独立进程只背负它兑现得起的承诺**：影像进程不实现查询与勾稽，占位实现 `StandaloneInvoiceFacade` 就够了。

## 5. 真要物理切开之前，先补齐这几件事

1. **外键与 join**：跨库以后，任何"档案 join 报销单""发票 join 收货行"的 SQL 都会失效。先按第 4 节的门面清点，把留在 SQL 里的跨域 join 换成两段取数。
2. **事务边界**：`@Transactional` 只覆盖一个连接。切库后一个业务动作跨两库的写，要么走"主库写＋他库补偿"，要么显式改成最终一致，不要指望它自动回滚。
3. **号段与幂等**：所有编号必须留在 `master`（第 2 节），切库时别把号段表一起搬走。
4. **只读副本的滞后**：报表走 `replica` 之后，刚提交的单在副本上可能晚几秒才看得见。列表页与追溯链要按这个前提写文案，别把"查不到"写成"不存在"。
5. **建库脚本**：`fssc_image` 的建库语句在整库导出里（`db/Dump<导出日期>/`）；`document`／`invoice` 真要独立成库时，得先给出它们的建库与迁移脚本。

## 6. 值不值得拆

按**扩容曲线**和**故障半径**判断，不按时髦程度：

- 影像：体积增长最快、单请求最重（原件上传/预览），且挂了不影响开单审批 → 最先拆，已经拆了。
- 报表/追溯：读多写少、偶发大查询，容易拖垮主库连接池 → 用 `replica` 路由键分流即可，不必先拆进程。
- AI 网关：外部模型调用的延迟不可控，需要独立超时与配额 → 独立进程，关掉它不影响任何人工页面。
- 发票/档案：数据量大但事务与单据强耦合 → **先分库路由、暂不分进程**，等 join 清点做完再说。
