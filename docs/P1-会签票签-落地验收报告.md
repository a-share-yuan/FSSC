## 二、实现原理

### 2.1 BPMN 生成（`WfBpmnTemplateService.build()`）

节点 `wf_node_config.multi_type ∈ {ALL, SEQ, VOTE}` 时，为该 userTask 生成
`multiInstanceLoopCharacteristics`：

```xml
<bpmn:multiInstanceLoopCharacteristics isSequential="true|false"
        flowable:collection="${<nodeKey>_assignees}" elementVariable="assignee">
  <bpmn:completionCondition xsi:type="bpmn:tFormalExpression">
    ${<nodeKey>_approvedCount * 100 &gt;= <ratio> * nrOfInstances
      || <nodeKey>_rejectedCount * 100 &gt; (100 - <ratio>) * nrOfInstances}
  </bpmn:completionCondition>
</bpmn:multiInstanceLoopCharacteristics>
```

- `ALL`：`isSequential=false`，完成条件 = 全部实例办完（Flowable 默认）
- `SEQ`：`isSequential=true` → 逐个派发
- `VOTE`：完成条件用节点前缀计数器，**票数达线即提前收口**

### 2.2 启动期注入（`WfEngineFacade.injectMultiInstanceVars`）

`start()` 阶段按 `model_key` 读本流程所有多实例节点，注入：

| 变量 | 用途 |
|---|---|
| `<nodeKey>_assignees` | `flowable:collection` 取数源（在办候选人 user-id 列表） |
| `<nodeKey>_miTotal` | 应到人数（进度展示） |
| `<nodeKey>_multiType` | `ALL/SEQ/VOTE`（BPMN 只有 `isSequential` 布尔，区分不出"并行会签"与"票签"） |
| `<nodeKey>_voteRatio` | 票签阈值（仅 VOTE） |
| `<nodeKey>_approvedCount` / `_rejectedCount` | 票数计数器初值 0（仅 VOTE） |

候选解析复用既有链路 `candidatesInScope` / `sanitizeApprover`，并施加 `approve.deny_self` 自审回避。

### 2.3 计票（`WfEngineFacade.countVoteIfNeeded`）

`complete()` 内、`taskService.complete()` 之前累加计数器 → 与 BPMN `completionCondition`
**同一公式**判定收口，不存在"两处口径漂移"。逐票留痕复用 `wf_task_history`，**不新建计票表**
（避免同一事实两处留痕、日后必然漂移）。

## 三、本轮修掉的 3 个真实缺陷（都会静默降级，必须记住）

### 缺陷 ①：启动期读不到 `wf_node_config` → BPMN 无多实例块

- **根因**：`deployBizFlows()` 里 `runIgnoreTenant` **只裹了** `wfBusinessFlowMapper.selectList`，
  而 `build()`（内含 `attachMultiType → wfNodeConfigMapper.selectOne`）落在 lambda **外面**；
  而 `FsscTenantLineHandler.getTenantId()` 是 **fail-closed** → 启动期无租户上下文直接抛 → 被 `catch` 吞掉
  → `multiType` 恒 `null` → 生成普通单任务节点。
- **欺骗性**：同一个模板接口在**带租户的 HTTP 请求里调用是对的**，只有**启动部署**是错的。
- **修法**：把**整个部署循环（含 `build()`）**包进 `runIgnoreTenant`。
- **实证**：修复前后对比部署产物 `ACT_GE_BYTEARRAY.BYTES_` —— 修复前无 `multiInstanceLoopCharacteristics`，修复后存在。

### 缺陷 ②：`applyNodeConfig` 覆盖多实例元素变量 → 顺序会签三轮同一人

- **根因**：`complete()` 之后 `assignApprover → applyNodeConfig → tryResolveAssignee` 对 `ROLE` 型节点
  取**角色首个持有人（3797）** 并 `setAssignee`，**把 BPMN 元素变量逐实例写好的值覆盖掉**。
- **现象**：SEQ 三轮全部 3797；并行 ALL 因实例记录尚未落库而"侥幸"躲过，掩盖了问题。
- **判读证据**：`ACT_RU_VARIABLE` 中元素变量已推进（`assignee=3820`、`loopCounter=1`），
  而新任务 `ASSIGNEE_` 仍是 `3797` ⇒ **创建后被覆盖**，不是取数错。
- **修法**：`multi_type ∈ {ALL, SEQ, VOTE}` 的节点**直接跳过**指派覆盖，取人权交还 BPMN。

### 缺陷 ③：前后端词表漂移 `SEQUENTIAL ≠ SEQ` → 静默退化为单人审批

- **根因**：后端按 **DB 列注释**定义词表 `ANY/ALL/SEQ/VOTE`；
  前端 `constants/enums.js` 自写 `ANY/ALL/SEQUENTIAL`（`SEQ ≠ SEQUENTIAL`，**且没有 `VOTE`**）。
  配置者选"顺序会签"，后端不识别 ⇒ 静默按单人节点生成，**无任何报错**。
- **修法（两道闸）**：
  1. **写入闸**（`WfNodeConfigService.normalizeGovernance`）：`multi_type` 只收 `ANY/ALL/SEQ/VOTE`
     （自动大写归一），`VOTE` 时 `vote_ratio` 必须 `1..100`，非法即 `PARAM_INVALID` **fail-fast 拒绝**；
     报错节点名按 `nodeName → nodeKey → #id` 逐级兜底。
  2. **前端对齐**：词表改成后端词表；并清理过时注释
     （`BpmnDesigner.vue` 原写"会签后端无消费方、控件已摘除"，早已不成立）。

## 五、验证方式（可复现）

```bash
# 1. 登录（租户 DEMO1）
POST /api/auth/login  {subjectType,tenantCode,username,password}

# 2. 起流程（隔离测试入口，不产生真实单据）
POST /api/tenant/wf/dev/start  {bizType: "MI_TEST"|"MI_SEQ"|"MI_VOTE"}

# 3. 审批（必须用任务实际 assignee 对应账号登录）
POST /api/tenant/wf/approve  {taskId, approved, comment}

# 4. 进度
GET  /api/tenant/wf/mi-progress?taskId=xxx
```

校验脚本：`_tmp_p1_verify.py`（三变体端到端）、`_tmp_p1_gate.py`（写入闸）、`_tmp_p1_progress.py`（进度接口）。

>  **校验读库禁用长连接**：pymysql 默认非 autocommit + REPEATABLE READ，
> **同一条连接里第一次 SELECT 就钉住快照**，后续查询看到旧数据（曾因此误判"3 票投完任务还在"）。
> 一律 `autocommit=True`。
>
>  **读部署产物别用 `ORDER BY ID_ DESC`**：新旧 jar 的启动部署会交叉落库，
> 按自增 id 取到的可能是上个进程留下的旧版本，会得出"新代码没生效"的假结论。用 `ORDER BY VERSION_ DESC`。
