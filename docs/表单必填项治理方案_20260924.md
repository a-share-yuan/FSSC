# 表单必填项治理方案（全页面盘点 + 三层收口）

> 生成日期：2026-09-24　执行范围：`fssc-web/src/views`（127 个 .vue）＋ `fssc-server`（150 个 Controller）＋ `fssc` 库
> 触发：用户指令「对所有页面的必填项进行检查（合同号/客户编号/客户编码/单据编号等），所有必填项前加红色 \*，所有表单提交前做必填项检查」
> 本方案所有数字均为脚本实测，非估算；取证脚本口径见 §7。

## 一、结论摘要

**必填约束在三层全部缺失，且已产生真实脏数据。**

| 层 | 应有 | 实测 | 判定 |
|---|---|---|---|
| 前端红星（视觉） | 必填项带 `*` | 196 个 `el-form-item` 写了 `required` 但**没有 `prop`** → 星号显示、校验为 0 | **假红星** |
| 前端校验（行为） | 提交前 `validate()` | 77 个含表单页面中仅 **11** 个真的调用了 `.validate()` | 66 个页面裸提交 |
| 后端校验 | `@Valid` + `@NotBlank` | 全仓仅 **22 个 `@NotBlank` ＋ 2 个 `@NotNull`**，分布在 **5 个文件**／150 个 Controller；`ContractController.create(@RequestBody ContContract)` 无任何校验 | 形同虚设 |
| 数据库约束 | 关键列 `NOT NULL` | `cont_contract` 33 列中**只有 `id` 是 NOT NULL 无默认值**；`crm_customer` 同样 0 个业务必填列 | 完全放开 |
| 校验异常兜底 | 400＋可读文案 | **已具备**：`GlobalExceptionHandler:58-63` 已有 `MethodArgumentNotValidException`/`BindException` → `PARAM_INVALID`＋字段级文案分支 | 可直接加 `@Valid`，无需补兜底 |

**已经漏进去的脏数据（这就是后果，不是理论风险）：**

- `cont_contract`：19 条合同中 **4 条 `contract_no` 为 NULL**，其中
  - `#48 批次3 R4 真跑·服务采购合同` **状态 APPROVED**——一张**已生效但无合同号**的合同；
  - `#47` 处于 APPROVING（审批中无号）；`#44/#46` DRAFT。
- `crm_customer`：37 条客户中 **2 条 `customer_code` 为空**，含 `#38 湖南华信制造有限公司`（真实名称、无编码，下游单据按编码引用时必然取不到）。
- 对照组：`exp_bill.bill_no` 因数据库层 `NOT NULL` ＋后端 `BizNoGenerator` 生成，**空值 0 条** ⇒ 说明「有约束就有数据质量」，反之亦然。

1. `views/master/Customer.vue:46-48`
   ```html
   <el-form :model="crud.form" :rules="customerRules" ...>   <!-- 无 ref -->
     <el-form-item label="客户编码">…                        <!-- 无 prop -->
     <el-form-item label="客户名称">…                        <!-- 无 prop -->
   ```
   而 `:114` 的 `customerRules` 明明写了 `customerCode/customerName/customerType` 三条 `required` ——
   因无 `prop`＋无 `ref`＋`useCrud.save()`（`composables/useCrud.js:58-71` 直接 `api.create`）**不校验**，规则 100% 失效。
   ⇒ 用户点名的「客户编码／客户编号」正是这条通路。
2. `views/contract/Contract.vue:59-62`
   ```html
   <el-form ref="formRef" :rules="formRules" ...>
     <el-form-item label="合同号"><el-input v-model="form.contractNo" .../>   <!-- 无 prop、无 required -->
     <el-form-item label="合同名称">…                                          <!-- 无 prop、无 required -->
   ```
   全文件**无一处 `.validate(`**；后端 `ContractService.create` 只回填 `companyId`，不查 `contractNo`。
   ⇒ 「合同号可为空」是前后端合谋的结果，最终产出上面那张 APPROVED 无号合同 #48。
3. 星号机制说明：Element Plus 的红色 `*` 只在 ①`el-form-item` 带 `required` 属性，或 ②`prop` 命中的 rules 里有 `required:true` 时渲染；
   而 `form.validate()` 只遍历**有 `prop`** 的项。故「有星号≠有校验」。930 个表单项里只有 129 个带 `prop`（13.9%），即 **86% 的字段物理上无法被校验**。

## 三、编号语义三分法（决定谁该加红星，最关键的业务判断）

「所有编号都必填」不能一刀切，因为三类编号的产生方式完全不同：

| 类别 | 例子 | 现状 | 应否加红星＋必填校验 |
|---|---|---|---|
| **① 人工录入型编号** | 合同号 `contract_no`、客户编码 `customer_code`、供应商编码、银行账户、预算方案编码 | DB 可空、后端不校验、前端无 prop | **要**：红星＋提交前校验＋唯一性（这是本次主战场） |
| **② 系统生成型编号** | 单据编号 `bill_no`（`BizNoGenerator`）、凭证号 `voucher_no`、流程实例号 | DB `NOT NULL`＋后端生成 | **不要**做人工必填：新建表单里它本就是空/只读，标红星反而误导；应显式只读＋文案「保存后系统生成」 |
| **③ 引用带出型编号** | 报账单上的合同号、付款单上的客户编码 | 由选择器带出 | **视场景**：若该单据类型要求关联合同（如服务采购付款）则必填，否则选填 —— 需按单据类型配置，见裁决 Q2 |

补充实测：`cont_contract.contract_no` **无唯一索引**（当前重复组 0，属未爆雷）；一旦定为人工必填，唯一性必须同时落 DB 索引＋后端查重，否则前端校验拦不住并发/导入（`ContractImportController:68` 就是直接 `setContractNo(f[0])` 走 Excel 导入，绕过一切前端校验）。

## 四、治理机制设计（不做 66 次同样的手工活）

### 4.1 单一口径来源：`src/constants/requiredFields.js`
按「模块 → 表单 → 字段 → 是否必填/触发时机/提示文案」集中声明，前端星号、前端校验、后端注释、方案文档同出一门，避免各处手写 rules 漂移。

### 4.2 前端三层收口
1. **prop 补齐**：脚本化 codemod，从每个 `el-form-item` 内子控件的 `v-model="form.xxx"` 反推字段名写入 `prop`（930 项中 801 项缺 prop，逐行手改不现实）。
2. **统一提交闸门**：新增 `useSubmitGuard(formRef, fn)` —— `save/submit` 一律 `await validate()` 不通过即中止＋`ElMessage` 聚焦第一个错误字段；替换 66 个页面的裸提交。
3. **红星真值化**：`required` 属性只允许由 rules 派生（禁止裸写 `required` 造成假红星）；`el-form` 统一 `:require-asterisk-position="'left'"` 保持视觉一致。

### 4.3 后端兜底（前端校验永远可被绕过）
1. 写接口入参从裸实体改为 DTO ＋ `@NotBlank/@NotNull`（先覆盖主数据与单据创建：合同、客户、供应商、银行账户、预算、发票、付款计划、PO）。
2. `GlobalExceptionHandler` 补 `MethodArgumentNotValidException` / `ConstraintViolationException` → `400 PARAM_INVALID`＋字段级文案，否则加了 `@Valid` 用户只会看到一个 500。
3. Excel 导入通道（`ContractImportController` 等）同口径逐行校验并回报行号——这是目前最大的旁路。

### 4.4 数据库终态（须先清洗存量，见 §5）
`contract_no`/`customer_code` 等 → `NOT NULL` ＋ `UNIQUE(tenant_id, xxx)`。
**注意执行顺序**：现在直接 `ALTER ... NOT NULL` 会因 4 条 NULL 合同、2 条空客户编码而失败（MySQL 严格模式报 1138/1048）。必须先补号或作废存量，再上约束。

### 8.4 运行期验证顺手修掉的四处口径不一致

1. **机票结算的死角**：`CorpPay` 遗留检查 `subType !== 'AGENCY' && !customerId` 在 `AIR` 下要求往来单位，而该页专属的往来单位选择器只按 `PREPAY/SETTLE` 渲染 ⇒ 提交被拦成无解。已改为与登记表同口径（仅 `PREPAY/SETTLE` 必填）。后端 `assertPayeeAccount` 本就不强制 `AIR` 的 `customerId`，故不放宽资金安全口径。
2. **出差申请的过度必填**：借款信息是选填区块，但「预计还款日期」无条件 `required` ⇒ 不借款的出差申请也提交不了。改为按 `extJson.loanAmount > 0` 动态必填（同时把账户名称/收款账号/开户行纳入同一条件），实测：金额留空时四颗星全部消失，填 5000 后四颗星全部出现。
3. **恒有默认值的单选组不再挂假星**：`PreApply` 的「费用承担类型」与 `CorpPay` 同列字段去掉装饰性 `required`（不存在漏填，加星是假信号）。
4. **【P0 隐患】`{ required, message, trigger }` 三键规则会把合法输入判为非法**——本批次最深的一个坑。async-validator 的 `getValidationMethod`：规则去掉 `message` 后若**只剩 `required` 一个键**，走类型无关的 required 校验器；只要再多一个键（如 `trigger`），就改走 `string` 校验器，于是 `typeof value !== 'string'` 直接报 `x is not a string` ⇒ **下拉选中年份（2026）、申请人 ID、开关选「否」（false）、金额输入框里的数字，全部永远提交不过**。
   - 全仓实测：这种三键规则 **43 个文件 / 185 处**（`AssetCardTab` 14、`Login` 7、`Org` 8、`LoanApply` 10、`PreApply` 18、`FlowConfig` 9…）。此前这些页面几乎不调 `validate()`（死规则），所以问题被"掩盖"；一旦批次 2 接上闸门就会集中爆雷。
   - 处置：脚本化剥掉这类规则的 `trigger` 键（185 处一次改完，43 文件），`useFormRules.commonRules` 同步改造（`select/date/required` 一律不带 trigger，金额用 `type: 'number'`，文本用 `whitespace`）。`billRequired.billRules()` 因自带 `validator` 函数，从来不走该分支，不受影响。
