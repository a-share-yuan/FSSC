## 二、多租户隔离设计（本设计的核心）

### 2.1 四条铁律

所有租户业务表**无条件**遵守，由 `scripts/db-check.py` 在提交前强制校验：

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | `tenant_id bigint NOT NULL`，**紧跟 `id` 之后** | 位置固定后，代码审查扫一眼就知道这表受不受管；`BaseEntity` 映射也统一 |
| 2 | **任何唯一索引必须以 `tenant_id` 打头** | 否则 A 租户建了编码 `U001`，B 租户永远建不了。这是最经典、也最难在测试环境复现的 SaaS 事故 |
| 3 | 必须有一个 **以 `tenant_id` 打头的普通索引** | 拦截器改写后每条 SQL 都带 `WHERE tenant_id=?`，没有前导索引则全表扫描 |
| 4 | **审计表不带 `del_flag`** | 日志只能归档不能删。留了删除位，就一定会有人去删 |

### 2.2 命名约定：`tenant_id` vs `ref_tenant_id`

**平台表也需要记录"这条数据属于哪个租户"**（订单、账单、用量统计），
但这里的语义是**业务外键**，不是隔离字段。

本设计强制：**平台表一律命名 `ref_tenant_id`，绝不叫 `tenant_id`。**

> 为什么较真这一点？
> 让"列名叫 `tenant_id`"成为"该表必须参与租户改写"的**绝对信号**。
> 一旦允许平台表也叫 `tenant_id`，将来有人把 `pf_order` 误加进拦截器，
> 平台端所有查询会被静默追加 `WHERE tenant_id = ?` —— 不报错，只是永远查不出数据。
> 这类问题排查成本极高。用命名把歧义消灭在写代码之前。

涉及表：`pf_tenant_package`、`pf_order`、`pf_bill`、`pf_tenant_stat`。

### 2.3 显式豁免机制

规则要有牙齿，但也要允许有充分理由的例外——**例外必须显式声明、可被审计**。

在 SQL 中用注解声明：

```sql
-- @allow-global-unique: token 是 32 位随机串，必须全局唯一而非租户内唯一。
-- 下载接口校验 token 时尚未建立租户上下文（token 本身就是身份凭据），
-- 若改成 (tenant_id, token) 会退化成"猜中 token 即可跨租户下载"。
UNIQUE KEY `uk_token` (`token`),
```

自检脚本识别该注解后，将其列入"显式豁免"清单单独输出，而不是当作违规。

当前全库仅 **1 处**豁免：`sys_file_token.uk_token`。

### 2.4 平台字典与租户字典物理分表

| 表 | 归属 | 说明 |
|---|---|---|
| `sys_dict_type_def` / `sys_dict_data_def` | 平台，无 `tenant_id` | 内置字典**模板** |
| `sys_dict_type` / `sys_dict_data` | 租户，有 `tenant_id` | 租户开通时从模板复制一份，之后各改各的 |

不做成一张表（用 `tenant_id = 0` 表示公共），是为了避免"`tenant_id` 可以为 0/NULL"这个口子——
一旦开了口子，铁律 1 就不再是铁律。

## 三、关键表设计说明

### 3.1 `exp_bill` — 统一单据主表（ADR-6）

事前申请、费用报销、员工借款、借款还款、对公支付，五类单据**共用一张主表**，
用 `bill_type` 区分。

**理由**：这五类单据的头信息高度同构（申请人 / 部门 / 公司 / 金额 / 状态 / 流程实例），
差异只在明细行。合并后，流程引擎对接、待办列表、审批留痕、附件、发票、支付
全部只需一套代码；新增单据类型只加一个枚举值。

**代价**：主表字段偏多，部分字段对某些类型无意义（如 `loan_balance` 只对 `LOAN` 有效）。
在"分模块交付"的节奏下，这个代价远小于维护五套近似代码。

**状态机**：

```
DRAFT ──提交──> APPROVING ──通过──> APPROVED ──推共享──> AUDITING
  ^                 │                                      │
  │                 └──驳回──> REJECTED ──重新编辑──┐       ├─审核退回─> AUDIT_BACK ─┐
  └──────────────────────────────────────────────┘       │                        │
                                                          ↓                        │
                                              PAYING ──> PAID ──> ACCOUNTED ──> CLOSED
```

每次状态迁移都写一条 `exp_bill_trace`（审计表，不可删），与流程引擎的
`wf_task_history` 互补：前者记录**业务状态**，后者记录**审批动作**。

### 3.2 `wf_*` — 为什么要冗余流程数据

Flowable 引擎负责**流转**，`wf_*` 负责**查询与留痕**。三个理由：

1. `ACT_*` 表的 `TENANT_ID_` 是 varchar，且引擎内部查询**不受** MyBatis-Plus 租户拦截器管辖——
   直接查引擎表是隔离的盲区。
2. 待办列表要按"部门、单据类型、金额、申请人"过滤排序，
   跨 `ACT_RU_TASK` 与业务表联查性能极差。
3. 引擎历史数据会被清理策略删掉，而审批留痕必须永久保存。

双写由 `WfEngineFacade` 统一保证，业务代码**不允许**直接调用 Flowable API。

### 3.3 `bg_occupy` — 预算流水只增不改

预算的四个金额（`total` / `adjust` / `occupy` / `used`）都在 `bg_item` 上，
但**任何变化都必须先写一条 `bg_occupy` 流水**，再更新汇总。

绝不允许直接 `UPDATE bg_item SET occupy_amount = ...`——
对不上账时，没有流水就无从追溯。

可用额度 = `total_amount + adjust_amount - occupy_amount - used_amount`

### 3.4 `inv_invoice` — 发票查重

唯一索引 `(tenant_id, invoice_no, invoice_code)` 保证同一租户内一张票只能录一次；
`is_used` / `used_count` 拦截重复报销。

发票池是租户级共享的——A 部门报过的票，B 部门再报会被直接拦下。

### 3.5 双轨审计

| 表 | 记录谁的操作 | `tenant_id` | `del_flag` |
|---|---|---|---|
| `pf_oper_log` / `pf_login_log` | 平台超管 | 无 | 无 |
| `sys_oper_log` / `sys_login_log` | 租户用户 | 有 | 无 |

物理分表而非一张表加标志位，原因同 2.4：不给 `tenant_id` 留空值口子。

## 四、通用字段规范

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `bigint AUTO_INCREMENT` | 主键。**不用雪花 ID**——单库场景下自增更省空间、索引更紧凑；对外展示的单号另由编号规则引擎生成 |
| `tenant_id` | `bigint NOT NULL` | 隔离字段，第 2 列 |
| `create_by` / `create_time` | `bigint` / `datetime` | 由 `MetaObjectHandler` 自动填充 |
| `update_by` / `update_time` | `bigint` / `datetime` | `ON UPDATE CURRENT_TIMESTAMP` |
| `del_flag` | `tinyint NOT NULL DEFAULT 0` | 逻辑删除。审计表**不设此字段** |
| 金额 | `decimal(20,2)` | 绝不用 `float`/`double` |
| 汇率 | `decimal(20,10)` | 10 位小数 |
| 税率 | `decimal(6,4)` | 如 `0.0600` |
| 状态/枚举 | `varchar` + **全大写英文码** | 如 `NORMAL` / `APPROVING`。**禁止用中文做 DEFAULT** |

> **关于中文 DEFAULT 值的教训**：初版 `op_voucher.voucher_word` 写了 `DEFAULT '记'`，
> 在 Windows 版 mysql 客户端下直接 `ERROR 1067 Invalid default value`。
> 已统一改为 `JOURNAL/RECEIPT/PAYMENT/TRANSFER`。

## 五、自动化质量守护

### 5.1 两层校验

| 脚本 | 校验对象 | 使用时机 |
|---|---|---|
| `scripts/db-check.py` | 静态解析 `db/*.sql` | 提交代码前、CI 流水线 |
| `scripts/db-check-live.py` | 连真实库查 `information_schema` | 部署后确认，检测 SQL 文件与库的**漂移** |

在线校验能覆盖静态检查做不到的三件事：

1. **中文注释乱码检测**
2. **字符集统一性**（是否全部 utf8mb4）
3. **野表检测**（库里有、SQL 文件里没有的表 = 有人手工改过库）

### 5.2 字符集陷阱（必读）

Windows 版 mysql 客户端**默认 GBK**。直接 `mysql < xxx.sql` 会把 UTF-8 的中文注释
按 GBK 解释，**建表照样"成功"，但所有 COMMENT 变成乱码**，且事后无法从库里恢复。

因此 `db-init.sh` 强制加了 `--default-character-set=utf8mb4`，这个参数不能省。

### 5.3 执行方式

```bash
# 一键初始化 + 自检
./scripts/db-init.sh

# 单独跑静态自检
python scripts/db-check.py

# 单独跑在线校验
MYSQL_BIN="/c/Program Files/MySQL/MySQL Server 8.0/bin/mysql.exe" \
  python scripts/db-check-live.py
```

### 5.4 当前验证结果

```
静态自检：PASS（69 张业务表合规，1 处显式豁免）
在线校验：PASS（89 张表，utf8mb4 统一，注释无乱码）
```

## 六、后端落地要点（供 P1 阶段参考）

1. **`BaseEntity`** 持有 `tenantId`，标注 `@JsonIgnore` —— 永不出现在 API 出参中。
2. **`MetaObjectHandler`** 在 insert 时**强制覆盖** `tenantId`（不是"为空才填"），
   杜绝前端传值污染。
3. **`TenantLineInnerInterceptor`** 必须注册在**分页拦截器之前**，
   否则 `count` 语句不带 `tenant_id`，会泄露数据规模。
4. **`ignore-tables`** 白名单与本文档 §一 的 20 张平台/全局表严格一致。
5. **跨租户聚合**（平台运营看板）走 `TenantContext.runIgnoreTenant()`，
   且**只允许聚合**，不得返回明细。
