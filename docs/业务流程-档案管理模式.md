# 档案集中管理与非集中管理模式（含流程差异）

> 适用版本：V1.4.92 / V1.4.93（2026-10-24）。
> 事实来源：代码实测（`DeliveryService`、`SharingService`、`BillArchiveService`、`WfProcessConfigService`）、
> 数据库实测（`sys_company`、`wf_process_config`、`wf_model`、`wf_node_config`）与当日两条真跑单据
> （`BX202610240004` 非集中、`BX202610240005` 集中）。节点名、角色码一律取流程定义原文。

## 1. 两种模式是什么

档案管理模式描述的是**纸质原件是否集中到财务共享中心**，不是单据审批链本身：

| 维度 | 集中管理（CENTRAL） | 非集中管理（NON_CENTRAL） |
|---|---|---|
| 纸质原件去向 | 原单位 → 寄送/交接至共享中心 | 留在原单位，不寄送 |
| 扫描岗 | 有：审批链内含扫描节点（`CLAIM`/`SETTLE` 为首节点；`FA_ADD` 仅在建转固档；`FA_TRANSFER` 为默认档） | 无：上述扫描节点全部移除，接续到原后继节点 |
| 实物签收 | 有：`op_physical_delivery` 登记，签收后共享作业链才激活 | 无：不产生签收单 |
| 单据交付状态 | `UNSIGNED` → `SIGNED` | 恒为 `NOT_REQUIRED` |
| 共享审核依据 | 纸质件扫描影像 + 电子附件 | 电子附件/影像（业务端上传） |
| 归档前置条件 | 实物必须已签收，`UNSIGNED` 不得归档 | 无实物签收要求，审批/作业完成后即可归档 |
| 电子发票 | 另有"无纸化"维度（`paperless=Y`）可免签收，与本模式相互独立 | 同左；非集中不等于无纸化 |

模式只影响**实物流**与**选哪支流程模型**；审批角色、金额授权档、凭证与归档动作在两种模式下保持一致。

## 2. 默认值：集中

- 数据库列默认值：`sys_company.archive_mode varchar(16) NOT NULL DEFAULT 'CENTRAL'`（实测 `SHOW COLUMNS`）。
- 新建/编辑公司表单默认值：`fssc-web/src/views/system/Org.vue` 的 `archiveMode: 'CENTRAL'`，下拉两项
  「集中管理 / 非集中管理」。
- 当前数据：9 家公司中 8 家 `CENTRAL`；仅公司 33（昆山，`AIG-KS`）为 `NON_CENTRAL`
  —— 这是 V1.4.93 的**单公司试点**，不是全局默认。
- 判定单点：`DeliveryService.isNonCentralArchive(companyId)` 直读 `sys_company.archive_mode`，
  其余代码（共享建链、归档前置闸、交付页提示）都复用它，不各自判库。

## 3. 模式如何决定用哪支流程

提交单据时 `WfProcessConfigService.resolveModelKey(bizType, subType, amount, companyId, deptId)`
按 `wf_process_config` 选模型：`company_id` 精确匹配优先，其次按 `priority` 降序。
V1.4.93 为公司 33 复制了 18 条规则（`priority=30`，高于现网集中规则），指向四支 `_NC` 模型：

| 业务入口（bizType / subType） | 集中模型 | 公司 33 命中 |
|---|---|---|
| `EXP_CLAIM` / `CLAIM`（含 `TRAVEL` 子类型） | `CLAIM` | `CLAIM_NC` |
| `EXP_PAY` / `PAY`（SETTLE、AGENCY、AIR、PREPAY 及通配） | `SETTLE` | `SETTLE_NC` |
| `GL_SALARY_PAY`、`GL_TAX_PAY` | `SETTLE` | `SETTLE_NC` |
| `FA_ADD`、`FA_CIP_TO_ASSET` | `FA_ADD` | `FA_ADD_NC` |
| `FA_TRANSFER`、`FA_TRANSFER_CROSS` | `FA_TRANSFER` | `FA_TRANSFER_NC` |

四支 `_NC` 模型均已在 2026-10-24 发布并部署（`wf_model.status=DEPLOYED`，`org_scope=ORG`、`org_ids=33`）。
路由与公司模式都是实时读库，改完不需要重启服务；流程定义发布即部署到引擎。

> 覆盖核对：现役库 `wf_model` 中**含扫描岗的模型恰好只有这四支**（实测 `bpmn_xml LIKE '%SCAN_STAFF%'`
> 仅 `CLAIM`、`SETTLE`、`FA_ADD`、`FA_TRANSFER` 命中），因此公司 33 的审批类流程已全部有非集中变体。
> `bpmn-repo` 快照中的 `INV_DISPOSE`、`INV_DISPOSAL_EXEC`、`INV_INTERNAL_SALE`、`FM_DOC_FLOW` 等历史模型
> 不在现役 `wf_model` 中（无法发起），不构成"漏改造"；若日后重新启用，须先补 `_NC` 变体。

## 4. 两种模式的流程对照（以费用报销为例）

### 4.1 集中管理

```
提交 → [扫描单据 SCAN_STAFF] → [实物交接/寄送 op_physical_delivery] → [签收]
     → [共享审核 FSSC_AUDITOR] → 金额授权档 → [预制凭证审核] → 结束
     → 共享作业链：AUDIT → PAY → BOOKKEEP
     → 归档（要求 delivery_status=SIGNED）
```

1. 提交后系统按公司/部门/金额选集中模型，首节点为扫描岗。
2. 建链时登记 `op_physical_delivery`（PENDING），共享作业链首个任务 `active_flag=N`（不可认领）。
3. 共享支持岗/扫描岗签收（`SIGNED`）后，首任务激活，作业池可见。
4. 实物未签收（`UNSIGNED`）时，归档执行会被跳过并在日志中提示。

### 4.2 非集中管理

```
提交（电子附件） → [直属上级] → [部门经理] → [项目经理] → [共享审核 FSSC_AUDITOR]
                → 金额授权档 → [预制凭证审核] → 结束
                → 共享作业链：AUDIT → PAY → BOOKKEEP
                → 归档（NOT_REQUIRED 不阻断）
```

1. 提交后命中 `_NC` 模型，定义里没有扫描节点，首节点就是审批人。
2. 建链时判定为非集中：写 `exp_bill.delivery_status=NOT_REQUIRED`，**不建**签收单，首任务直接 `active_flag=Y`。
3. 纸质原件留在原单位；共享审核只看业务端上传的电子附件/发票影像。
4. 归档前置闸对 `UNSIGNED` 的拦截在非集中公司不生效（V1.4.92 起）。

## 5. 四支非集中模型与集中模型的节点差异

节点差异取自现役 `wf_model.bpmn_xml`（与 `bpmn-repo/models/<流程码>/latest.bpmn20.xml` 快照同步）：

| 模型对 | 非集中相对集中 | 说明 |
|---|---|---|
| `CLAIM` → `CLAIM_NC` | 仅移除 `Task_2 扫描单据【财务扫描岗】` | 其余节点（含 `Task_14`/`ET_7`/`ETB_7` 预制凭证审核、`ET`/`ETB` 招待费两档）与集中版一致 |
| `SETTLE` → `SETTLE_NC` | 仅移除 `Task_2 扫描单据【财务扫描岗】` | `Task_14_R 付款凭证复核`、`Task_11 财务总监审批` 多实例两版都有 |
| `FA_ADD` → `FA_ADD_NC` | 仅移除 `FC_1 转固单据扫描【财务扫描岗】` | 其余转固节点不变 |
| `FA_TRANSFER` → `FA_TRANSFER_NC` | 仅移除 `FT_1 调拨申请登记【财务扫描岗】` | 其余调拨节点不变 |

实测口径：逐对解析现役 `wf_model.bpmn_xml` 的 `userTask id` 集合与 `conditionExpression`，四对的差集
都恰好是扫描节点本身（节点数 21→20、14→13、10→9、7→6），条件表达式逐条相同；`Task_11` 的
多实例属性（`${Task_11_assignees}`）两版一致。**非集中变体不是"改审批链"，只是摘掉扫描节点。**

`CLAIM_NC` 在共享审核节点 `Task_7` 上沿用集中版参与人方案（ROLE `FSSC_AUDITOR` ＋ POST `J0060`，OR），
该方案已由 V1.4.93 复制到 `CLAIM_NC`；其余节点由发布时生成的 `wf_node_config` 副本提供取人口径。

## 6. 单据与作业链上的可观察差异

| 观察点 | 集中 | 非集中 |
|---|---|---|
| `exp_bill.delivery_status` | `UNSIGNED` → `SIGNED` | `NOT_REQUIRED`（始终） |
| `op_physical_delivery` | 1 行（PENDING → SIGNED） | 0 行 |
| `op_audit_task` | AUDIT/PAY/BOOKKEEP 三环，签收前首环 `active_flag=N` | 同样三环，首环立即可认领 |
| 归档结果 | 签收前 `UNARCHIVED`，签收后可归档 | 作业完成后即可归档 |
| `exp_bill.archive_status` | `UNARCHIVED` → `ARCHIVED` | 同左 |
| `op_archive` | 一行，`archive_type=BILL`、`status=FILED` | 同左 |
| 电子发票无纸化 | 独立维度 `paperless=Y` 亦可免签收 | 非集中不会自动置 `paperless` |

## 7. 切换与回滚

### 7.1 切到非集中（单公司）

前置：`V1.4.92` 代码已上线（`isNonCentralArchive` 在位）；四支 `_NC` 模型可导入；目标公司原为 `CENTRAL`。

> 上线核对：除 V1.4.92 外，`CLAIM_NC` 还要求 `WfEngineFacade.resolveExpenseType` 把 `CLAIM_NC`
> 纳入报销类流程（向引擎注入 `expenseType` 分支变量）。缺该项时 `CLAIM_NC` 发起即抛表达式错误
> （`Gw_ENT` 取值失败），其余三支模型不受影响。

1. 在设计器导入并发布 `CLAIM_NC`、`SETTLE_NC`、`FA_ADD_NC`、`FA_TRANSFER_NC`（发布即部署）。
2. 执行 `fssc/fssc-server/sql/V1.4.93_archive_noncentral_switch.sql`：复制节点配置、参与人方案、
   18 条路由，扩齐套闸，最后一步才把公司模式从 `CENTRAL` 翻成 `NON_CENTRAL`。
3. 复点：公司模式、四支模型 `DEPLOYED`、节点配置行数（23/21/18/13）、路由 18 条、方案 1＋维度 2。

### 7.2 回滚

执行 `V1.4.93_archive_noncentral_switch_rollback.sql`：公司模式改回 `CENTRAL`、删除 33 的 `_NC` 路由、
节点配置、参与人方案副本与 `wf_model` 行，并从齐套键中移除追加片段。
Flowable 已部署的 `CLAIM_NC:*` 流程定义保留（无路由指向时不会被启动），删除引擎定义需另走停服窗口。

> 回滚后，原非集中单据已产生的 `NOT_REQUIRED`/归档记录不会回写；历史事实按当时模式解释。

## 9. 常见问题

- **非集中公司还会看到扫描岗吗？** 不会。现役含扫描节点的四支模型（`CLAIM`/`SETTLE`/`FA_ADD`/`FA_TRANSFER`）
  都已提供 `_NC` 变体并路由到公司 33；`op_audit_task` 也不生成扫描任务。只有从 `bpmn-repo`
  重新启用历史扫描类模型时才需要先补非集中变体。
- **非集中等于无纸化吗？** 不等于。`paperless` 是"发票介质/签收豁免"维度，非集中是"原件是否寄送"维度，
  两者可以任意组合。
- **改了公司模式要不要重启？** 不要。模式与路由都是实时读库；流程模型发布即生效。
- **已经签收/已经归档的单据改模式会怎样？** 不回写历史；新单按新模式，旧单保留原状态与档案记录。
