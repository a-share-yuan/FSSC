# 62 · 单据全链路联查「跨域串号 + 跳环节」缺陷整改报告

> 报障样本：**单据编号 CER1789602519664** —— 抽屉出现「提单灰 → 审批通过灰 → 生成凭证绿」的跳环节错乱。
> 结论：不是显示瑕疵，是**跨业务域串号**（把别域、别单据的数据画进了本单链路）。
> 状态：代码已改完并通过编译校验；**后端需重启 8089 后接口口径才生效**（见 §6）。

## 2. 根因证据链（四步，全部实测）

1. **抽屉拿到的是「本域业务表主键」，不是费用单据主键**
   57 个业务页统一写法：`<BillTraceDrawer v-model="traceVisible" :bill-id="traceBillId" />`，
   而 `traceBillId.value = row.id || row.billId || row.bill_id` —— 发票页传 `inv_invoice.id`、资本性支出页传 `fa_cer_request.id`（本例 = 22）。

2. **后端把任意 id 当 `exp_bill` 主键**
   `BillTraceChainController` 直接 `expBillMapper.selectById(billId)`。
   → id=22 在 `exp_bill` 查不到，单据主体为 `null`。

3. **下游按裸 id 关联，撞出无关单据（这才是「生成凭证绿」的来源）**
   凭证查询 `WHERE bill_id=22 OR source_doc_id=22` 命中：
   **`op_voucher` id=1364，`JZ2026091700022`，`source_type=GL_ACCRUAL`，摘要「E2E手工凭证」**
   —— 一张总账手工凭证，与这张资本性支出单毫无关系。
   → `summary.reached` 里被塞进 `VOUCHER`。

4. **时间线前两节的数据源来自另一个接口，且该接口有「仅限本人单据」守卫**
   `BillTraceDrawer` 用 `GET /expense/bill/detail/{id}` 拿 `billInfo.status` 驱动第 1/2 节；
   而 `ExpenseBillService.detail()` 走 `requireMine()`：**只要当前用户不是申请人就抛 4030「无权操作他人单据」**
   （实测 **admin 登录同样被拒**）。
   → `billInfo = null` → `status` 缺失 → 第 1 节副标题显示「—」、第 2 节判定为「待审批」灰。

> 于是：**第 1/2 节数据源断供（灰） + 第 3-6 节数据源正常但因串号而误亮（绿）= 看起来像跳过了一个环节。**
> 这解释了用户观察到的「不只是 admin 用户，任何用户都这样」——任何非申请人都必然触发。

## 3. 改动清单

### 3.1 后端 `fssc-server/fssc-start/.../expense/controller/BillTraceChainController.java`

| # | 改动 | 说明 |
|---|---|---|
| 1 | **锚点校验** | `exp_bill` 查不到该 id 即判定「非费用域单据」，返回 `scope=NOT_SUPPORTED` + 全空集合，**绝不用其它单据的数据填补** |
| 2 | **凭证来源白名单** | 新增 `VOUCHER_SOURCE_EXPENSE`（`EXPENSE / EXPENSE_PAY / EXP_LOAN / EXP_REPAY / EXPENSE_REIM / EXPENSE_LOAN / EXPENSE_REPAY`），`GL_*`、`FA_*`、`AP`、`AR`、`STOCK_*` 等同 id 凭证不得混入本单链路 |
| 3 | **补齐 APPROVED 环节** | `summary.reached` 增补 `APPROVED` 段，三档证据取或：**① 单据状态族**（APPROVED/PAID/POSTED/ARCHIVED/COMPLETED/REPAID/PARTIAL_REPAID/CLOSED）→ **② 流程实例终态**（wf_instance.status ∈ APPROVED/COMPLETED）→ **③ 下游已发生**（有凭证/付款/批次/档案，未审批不可能产出下游单据）；**负面状态一票否决**（REJECTED/WITHDRAWN/VOID/TERMINATED/CANCELLED） |
| 4 | **summary 扩字段** | 新增 `scope`、`billMatched`、`billStatus`、`approved`、`approvalEvidence`、`instStatus`、`currentNode`，供审计追溯判定依据 |
| 5 | 新增可选参数 `bizType` | 为后续按业务域路由预留，当前非费用域返回 `NOT_SUPPORTED` |

### 3.2 前端 `fssc-web/src/components/BillChainTimeline.vue`

| 项 | 改前 | 改后 |
|---|---|---|
| 环节判定口径 | 第 1/2 节读 `props.status`（来自另一个会被 4030 拦截的接口），第 3-6 节读 `chain.summary.reached` —— **两套数据源** | **6 节统一读 `chain.summary.reached`**，后端单一口径裁决，前端只做展示 |
| 状态→步骤映射 | 组件内**重复定义**了 `constants/billStatus.js` 的映射表（违反该文件「禁止重复定义」约定），且缺 `COMPLETED / REPAID / PARTIAL_REPAID` 等状态 → 这些单据恒灰 | 删除本地映射，改由后端 `summary.approved` 判定 |
| 驳回状态 | 无区分，一律「待审批」灰 | 新增 `blocked` 态：红圈 ✕ + 「已驳回 / 已撤回 / 已作废」文案 |
| 未接入域 | 照画 6 节（第 1 节强制绿） | `scope=NOT_SUPPORTED` 时**不渲染时间线** |

### 3.3 前端 `fssc-web/src/components/BillTraceDrawer.vue`

| 项 | 改前 | 改后 |
|---|---|---|

## 5. 影响面与后续计划

- **受益**：费用/借款/还款域约 10 个页面（expense/* 全系、requisition 工作台、我的单据、借款/还款）追溯链路口径统一、不再跳环节；任何用户（含管理员、审批人）查看他人单据都不再触发 4030 依赖。
- **代价**：其余约 47 个页面的追溯结果从「显示（但可能是别人的）数据」变为「明确提示未接入」。
  这是**把错误数据换成明确告知**，符合审计口径（宁缺勿错）；但如果这 47 个页面业务上确实需要追溯，属于待办而非回退。
- **第二批建议（待排期）**：给抽屉加 `biz-type` prop，后端按 `bizType` 路由到各域追溯实现 ——
  通用层（单号/标题/申请人/金额/当前节点/审批历史，数据源 `wf_instance` + `wf_task`）+ 财务层（凭证/付款/批次/归档）。
  按高频域推进：采购应付 → 发票 → 合同 → 资产 → 总账 → 其余。
