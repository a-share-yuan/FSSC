## 2. Flowable 8 的**能力边界**（决定"加签/撤销"能做成什么样）

用 `javap` 对 `flowable-engine-8.0.0.jar`（从运行 jar 内 `BOOT-INF/lib` 抽出）逐类核对，避免凭印象设计：

```
RuntimeService:
  createChangeActivityStateBuilder()                  ← 有：移动执行到指定活动
  addMultiInstanceExecution(activityId, parentExecId, vars)  ← 有：多实例追加成员
  deleteMultiInstanceExecution(executionId, cancel)
ChangeActivityStateBuilder:
  moveActivityIdTo(from, to) / moveActivityIdsToSingleActivityId(...) /
  moveExecutionsToSingleActivityId(...) / processVariable(s) / localVariable(s) / changeState()

ProcessInstanceModification*                          ← **不存在**
```

**三点结论**：

1. **没有** Activiti 风格的 `ProcessInstanceModification` ⇒ **无法在运行期动态插入 BPMN 节点**。
   「前/后加签 = 临时加一个节点」在 Flowable 8 上**做不到字面等价**。
2. 能做**等价语义**：加签＝把任务**临时改派**给加签人，加签人审完**回跳**给应得的人（不推进流程）。
   本轮即按此实现（§4.1）。
3. `ChangeActivityStateBuilder.moveActivityIdTo(from, to)` 是**「已办撤销回原节点」与「任意级次驳回」
   的正规原语**（≠ 本轮的"改派回跳"，它真的搬执行）。本轮**没有**用它做撤回 —— 理由见 §6。

**语义（关键，别与会签/转办混淆）**

```
前加签 BEFORE：  我 ──加签──> [S1 先审] ──回跳──> 我（继续审，然后才推进流程）
后加签 AFTER ：  我审完 ──推进──> 下一节点任务 T2 的办理人 A2 被临时换成 S1
                 S1 审完 ──回跳──> A2（A2 自己再审，之后才推进）
可再加签     ：  S1 也能对同一任务再加签 S2 ⇒ 记录天然嵌套，回跳取最近一条 ACTIVE 即可
多人链式     ：  signUsers 逗号分隔，按 seqIndex 依次签（一次多节点）
```

**两处钩子**

| 钩子 | 位置 | 行为 |
|---|---|---|
| ① 回跳（前/后统一） | `complete()` 越权/自审校验之后、`taskService.complete` **之前** | 若操作人正是本任务某条 ACTIVE 加签记录的**当期加签人**：`approved=true` → 交还（`exitAssignee`，空则 `unclaim` 退回候选组）并**`return`，绝不推进**；`approved=false` → 记录置 `CANCELLED` 并**放行到正常驳回兜底**（加签人驳回＝业务驳回） |
| ② 后加签生效 | `complete()` 末尾（委托回执之后） | 查 `srcTaskId` 的 PENDING 后加签 → 取推进后**活跃任务**；**恰好 1 条**才改派给加签人并 `bindTask`；`0`（流程已办结）或 `>1`（并联/多实例）→ 置 **`FAILED` 并站内信告知发起人** |

**默认零影响**：库中没有任何 `wf_add_sign` 行时，钩子①（`activeByTaskAndUser` 返回 null）与钩子②
（`pendingAfterByProc` 返回空表）都不产生任何写入与改派 ⇒ `complete()` 行为与改造前逐字一致。

**显式拒绝而非静默降级**（本项目的老毛病，这里刻意封住）

- 同一任务已有进行中的加签 → `addSign` **直接拒绝**（不做排队）：加签链顺序一旦被静默重排，留痕无法解释。
- 加签人校验：存在、`status=NORMAL`、**非 admin**（沿用「admin 禁入业务审批节点」铁律）。
- 后加签不生效 → 记录 `FAILED` + 站内信，**绝不静默**。

### 4.2 撤回（G3）：`allow_withdraw` 死配置接通

`WfEngineFacade.withdraw()` 增读 `wf_model.allow_withdraw`：

- 口径刻意 **fail-open**：仅当能查到模型**且该列显式为 0** 才拒绝；查不到 / 为 `NULL` **一律放行**。

## 6. 未做与为什么：`已办撤销回原节点` / `任意级次驳回`

- **能做的证据已有**：`ChangeActivityStateBuilder.moveActivityIdTo(curActivityId, targetActivityId)`。
- **本轮不做**：它是**搬执行**（真的把在办任务从 A 移到 B），一旦活动 id 选错、或目标节点重入被
  `applyNodeConfig`/多实例变量覆盖，**破坏的是在办单据本体**，属"改错比不改更糟"的一类。
  而当前**无任何运行期验证手段**（服务已停）⇒ 盲改风险不可接受。
- **建议路径**（待重启窗口，按序做）：
  1. 先做**只读预览**接口：给定 `procInstId`，返回"可回退到的上游节点"（来源 `wf_task_history` 的已办节点）+
     当前活动 id → 先让人看见"回到哪、谁会重新收到待办"；
  2. 再用 `moveActivityIdTo` 执行，并**用 `sys_config` 开关默认关闭**（`wf.revoke.enabled=0`）；
  3. 复验项：① 回退后 `wf_instance.current_node` 与待办一致 ② 原已办留痕保留（不删历史）
     ③ 回退节点的取人走 `applyNodeConfig`（不是拼历史 assignee）。
- `任意级次驳回`（G4）与它**同一原语**，可一并做。

| # | 场景 | 预期 |
|---|---|---|
| A-1 | 办理人对自己在办任务发起**前加签** | 任务办理人变为加签人；`wf_add_sign.status=ACTIVE`、`position=BEFORE`、`exit_assignee=`原办理人；留痕 `ADDSIGN`（含 targetUserId） |
| A-2 | 加签人在待办点「通过」 | **流程不推进**（实例仍在原节点）；任务办理人**回到原办理人**；记录 `status=DONE`；留痕 `ADDSIGN`（"前加签审完…已交还原办理人"） |
| A-3 | 原办理人再点「通过」 | 流程**正常推进**到下一节点 |
| A-4 | 加签人点「驳回」 | 实例终止（`terminateAsRejected`）、记录 `CANCELLED`、业务单据 `REJECTED` |
| B-1 | 办理人发起**后加签**后自己点「通过」 | 记录先 `PENDING`，推进后 `bindTask` 生效：**下一节点任务**办理人变成加签人、`exit_assignee=`下一节点原办理人 |
| B-2 | 加签人对下一节点任务点「通过」 | **不推进**；任务交还 `exit_assignee`（原办理人为空时退回候选组）；记录 `DONE` |
| C-1 | **多人链式**：`signUsers=U1,U2` | U1 审完 → 办理人变 U2（`seq_index=1`）→ U2 审完 → 交还 |
| C-2 | **可再加签**：加签人 U1 再加签 U2 | 嵌套生效；U2 审完回到 U1，而不是直接回原办理人 |
| D-1 | 同一任务重复发起加签 | **被拒**："该任务已有进行中的加签" |
| D-2 | 把 `admin` 作为加签人 | **被拒**："不允许把管理员加签为审批人" |
| D-3 | 非本任务办理人发起加签 | **被拒**：`403 只能对当前由你办理的任务发起加签` |
| E-1 | 加签人本人 `POST /add-sign/{id}/cancel` | 记录 `CANCELLED` 且任务**交还回跳目标**（不卡在已放弃的加签人手上） |
| E-2 | 非发起人/非当期加签人取消 | **被拒** 403 |
| F-1 | 后加签，但本节点是**流程最后一个**节点（推进后无任务） | 记录 `FAILED` + 发起人**收到站内信**；流程本身不受影响 |
