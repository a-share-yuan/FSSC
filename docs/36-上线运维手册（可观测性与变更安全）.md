## 一、可观测性（P0-B1）

### 1.1 健康探活

| 端点 | 鉴权 | 用途 | 返回 |
|---|---|---|---|
| `GET /api/health` | **免鉴权** | 业务自描述探活，给人与脚本看 | `{code:0,data:{status,components:{db,redis},version,uptimeSeconds,...}}` |
| `GET /actuator/health` | **免鉴权** | 标准 Actuator 聚合探活 | `{status:"UP"}`（含组件明细） |
| `GET /actuator/health/liveness` | **免鉴权** | K8s livenessProbe | `{status:"UP"}` |
| `GET /actuator/health/readiness` | **免鉴权** | K8s readinessProbe / SLB 摘除 | `{status:"UP"}` |
| `GET /actuator/info` | **免鉴权** | 发布核对版本 | 应用名/版本/编码 |

判定口径：`status` 为 `UP` 即健康；不健康时 `/api/health` 返回 `code=500` 并在 `components` 中指出是 `db` 还是 `redis`。

**K8s 探针建议**

```yaml
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8089 }
  initialDelaySeconds: 90     # 冷启动约 45–60s，需留余量
  periodSeconds: 20
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8089 }
  initialDelaySeconds: 60
  periodSeconds: 10
```

**两个坑（已在配置中规避，改动时注意）**

- `management.health.redis.enabled` 与 `management.health.mail.enabled` **默认必须为 false**。
  Spring Boot 只要类路径上有 `spring-boot-starter-data-redis` 就会注册 Redis 健康指示器，单机部署不连 Redis 时会把它判为 DOWN，导致 `/actuator/health` **恒为 DOWN**（而 `/api/health` 却是 UP，两者矛盾）。邮件同理：`spring.mail.host` 为空串时 `JavaMailSender` 仍被装配。
  → 多实例启用 Redis 后把 `management.health.redis.enabled` 改回 `true`；生产配置 SMTP 后按需打开 `mail`。

### 1.2 指标（Prometheus）

| 端点 | 鉴权 | 说明 |
|---|---|---|
| `GET /actuator/prometheus` | **需 Token** | Prometheus 抓取（文本格式） |
| `GET /actuator/metrics` | **需 Token** | 人工排查；`/actuator/metrics/http.server.requests` 看接口维度 |

设计取舍：探活必须匿名（探针没有 Token），但**指标不对公网匿名开放**——指标含全部接口面与容量信息。
启用 `management.endpoints.web.exposure.include` 时**刻意不含** `env`/`beans`/`configprops`/`heapdump`/`threaddump`/`shutdown`，防配置与内存泄漏。

可用指标（Micrometer 自动埋点，无需改代码）：

- `http_server_requests_seconds_count{uri,method,status,outcome}` —— QPS 与**错误率**（按 `outcome="SERVER_ERROR"` 过滤即 5xx）
- `http_server_requests_seconds_sum` / `_max` —— 累计耗时与最大耗时（除 count 得平均 RT，配合 histogram 出 P95/P99）
- `hikaricp_connections_*` —— 连接池活跃/空闲/等待
- `jvm_memory_used_bytes` / `jvm_gc_*` —— JVM 内存与 GC
- `flowable_*`（引擎自报）—— 流程实例相关

Prometheus 抓取配置示例（Token 方式）：

```yaml
scrape_configs:
  - job_name: fssc-server
    metrics_path: /actuator/prometheus
    scheme: http
    authorization:
      credentials: <一个长期有效的只读账号 Token>
    static_configs:
      - targets: ['10.0.0.11:8089']
```

推荐告警规则（阈值按容量压测结果校准）：

| 告警 | 表达式（示意） | 级别 |
|---|---|---|
| 接口错误率 > 1% | `sum(rate(http_server_requests_seconds_count{outcome="SERVER_ERROR"}[5m])) / sum(rate(http_server_requests_seconds_count[5m])) > 0.01` | P1 |
| P99 耗时 > 3s | `histogram_quantile(0.99, sum(rate(http_server_requests_seconds_bucket[5m])) by (le)) > 3` | P2 |
| 健康探活失败 | `up{job="fssc-server"} == 0` | P0 |
| 连接池打满 | `hikaricp_connections_pending > 0` 持续 5m | P1 |

### 1.3 全链路 traceId

- 每个请求由 `TraceIdFilter`（Order=0，早于鉴权/租户过滤器）生成 16 位 traceId，写入 SLF4J MDC。
- **响应头 `X-Trace-Id`** 原样回给调用方；支持上游透传（网关传入合法值则沿用，非法值丢弃重新生成，防日志注入）。
- 日志每行带 `[traceId]`，一次请求的全部日志可直接 grep 串联：

```bash
grep '\[617e274b423f488e\]' logs/fssc-server.log
```

> 用户报障时索取响应头 `X-Trace-Id`，即可在几秒内定位该次请求的全部日志——这是没有 APM 时最高性价比的排障手段。
> 非请求线程（启动、定时任务）traceId 为空，显示为 `[]`。

### 1.4 日志落盘

| 文件 | 内容 | 滚动策略 |
|---|---|---|
| `logs/fssc-server.log` | 全量（INFO 起） | 单文件 100MB / 保留 30 天 / 总量 3GB，自动 gz |
| `logs/fssc-error.log` | WARN 及以上 | 单文件 50MB / 保留 60 天 / 总量 1GB |

目录可用环境变量 `LOG_HOME` 覆盖（容器部署建议挂载到持久卷）。
另：`TraceIdFilter` 对耗时 ≥1s 的请求打 WARN，作为慢请求的兜底观测。

### 1.5 告警通道

`OpsAlertService` 面向**运维/值班**（区别于面向业务用户的站内信），触发点：

1. **定时任务失败**：`JobHeartbeatService` 捕获异常后，除推业务站内信，再推一条运维告警；
2. **健康探针状态翻转**：`HealthProbeJob` 每 5 分钟探测一次，`UP→DOWN` 报故障、`DOWN→UP` 报恢复（只在翻转时告警，不刷屏）。

配置（`application.yml`，或生产用环境变量覆盖）：

```yaml
fssc:
  notify:
    ops-webhook: ""        # 企微群机器人 webhook；空则回退用 wecom-webhook；再空则只落日志
    ops-mail-to: ""        # 运维邮件接收人，多个逗号分隔
    ops-alert-enabled: true
```

限流：同一标题告警 5 分钟内最多 5 条，计数走 `DistributedState`（多实例共享窗口）。
**限流设施故障时 fail-open 放行**——宁可多推一条，不可漏掉故障。

> 上线前请务必配置 `ops-webhook`，否则告警只落日志、无人值守时段等于没有告警。

## 二、变更安全（P0-B2）

### 2.1 发布流程（标准四步）

```bash
cd D:/SourceCode/Ashare/fssc

# ① 构建（含 87 项单测，失败即中止）
cd fssc-server && python ../scripts/mvn.py clean package && cd ..

# ② 启动候选版本并验证
bash scripts/run-server.sh --port 8089 --force-restart
curl http://127.0.0.1:8089/api/health          # 期望 code=0 / status=UP
bash scripts/verify-demo.sh                    # 冒烟
# 关键域 E2E（按改动范围选跑）
python scripts/_e2e_real_business_journey.py

# ③ 验证通过 → 存档为可回滚版本快照
bash scripts/release.sh snapshot --version 1.0.1
bash scripts/release.sh list

# ④ 记录发布（版本号 / 变更内容 / 验证人 / 时间）到发布记录
```

**铁律：没有 `release.sh snapshot` 的一版等于不可回滚的一版。** 先验证再快照，验证不通过就不要快照。

### 2.2 应用回滚（分钟级）

```bash
bash scripts/release.sh list                 # 看有哪些版本
bash scripts/release.sh rollback             # 回到上一版本（会二次确认，然后自动重启）
bash scripts/release.sh rollback --to fssc-server-1.0.0-20260910-200121.jar
```

回滚动作：停旧实例 → 用快照覆盖 `fssc-server/fssc-start/target/fssc-server.jar` → `run-server.sh` 重启 → 打 `/api/health` 验证。
快照保留最近 8 份，台账在 `releases/history.log`。

### 2.3 数据库迁移

现状：100 个 `V*.sql` 分散在 `db/sql`、`sql`、`fssc-server/sql`；现已建立**版本台账** `sys_schema_version`。

```bash
bash scripts/db-migrate.sh --status     # 已应用 / 未应用
bash scripts/db-migrate.sh --dry-run    # 将要执行的顺序（不落库）
bash scripts/db-migrate.sh              # 执行未应用迁移（**自动先全备**）
bash scripts/db-migrate.sh --baseline   # 首次接入既有库：只登记台账，不执行 SQL
```

规则：
- 只执行台账中不存在的版本，已应用的自动跳过；
- 单文件失败**立即中止**且不继续执行后续脚本（迁移必须严格有序）；
- 每份脚本记录 `sha256` 前 16 位，用于发现"同版本号内容被改"。

### 2.4 数据库回滚策略（重要）

**MySQL 的 DDL 不支持事务回滚**，因此本项目迁移是**前向单程**的。
回滚手段不是"给每个 V*.sql 写 down 脚本"（down 脚本本身也会写错，且 `drop column` 会丢数据），而是：

```bash
# 迁移前 db-migrate.sh 已自动全备：backup/<时间戳>/
# 需要回滚时：
bash scripts/restore-db.sh --dir backup/20260910-195911 --db fssc --force-prod
```

`restore-db.sh --force-prod` 会在灌回**之前**再给当前状态做一份 `backup/pre-rollback-<时间戳>` 快照，避免"回滚本身不可逆"。

> 因此**迁移窗口 = 备份窗口**：任何结构变更前必须有一次成功的全备，否则不允许执行迁移。

### 2.5 停机窗口与灰度 SOP

**一次标准发布的时间线（单机部署，预计 25–40 分钟）**

| 阶段 | 时长 | 动作 | 回退点 |
|---|---|---|---|
| T-24h | — | 发布评审：变更清单、影响域、回滚方案、验证清单三方确认 | — |
| T-30m | 5m | **发公告**：通知业务方停机窗口；确认无审批高峰期 | — |
| T-25m | 3m | **全备** `bash scripts/backup-db.sh`，确认 `[备份完成]` 且 gzip 校验通过 | — |
| T-20m | 5m | **停流**：Nginx 摘除后端（或提示前端"系统维护中"），等待在途请求结束（建议 60s） | — |
| T-15m | 3m | 停旧实例；记录当前快照名（`release.sh current`），确认有可回滚版本 | — |
| T-12m | 10m | **结构变更**：`bash scripts/db-migrate.sh`（自动再备一次） | 迁移失败 → 立即 `restore-db.sh --force-prod` |
| T-2m | 2m | 启动新版本：`bash scripts/run-server.sh --port 8089` | 启动失败 → `release.sh rollback` |
| T+0 | 5m | **验证**：`/api/health` + 冒烟 `verify-demo.sh` + 关键业务 E2E | 验证不过 → `release.sh rollback` |
| T+5m | 1m | **恢复流量**：Nginx 挂回后端 | — |
| T+5m–T+60m | 55m | **观察期**：盯错误率、P99 耗时、告警群、`fssc-error.log` | 异常 → 回滚 |
| T+60m | 5m | 发布记录归档；快照 `release.sh snapshot` 确认存档 | — |

**灰度（多实例部署后）**
1. 先只升级 1 台，`/actuator/health/readiness` 就绪后把少量流量导入；
2. 观察 15 分钟错误率与耗时，无异常再滚动升级其余实例；
3. 多实例必须 `fssc.redis.enabled=true`（`DistributedState` 切换 Redis），并注入**完全相同**的 `FSSC_JWT_SECRET`，否则会出现"同一用户被随机踢下线"。

**停机不可用窗口**（单机、无滚动能力时的真实停机时长）：约 **12–18 分钟**（停流→迁移→启动→验证）；
其余时间可在线进行（备份、构建、观察）。若需更短窗口，需部署双实例 + Nginx 灰度。

## 三、备份与恢复（P0-B3）

### 3.1 备份策略

```bash
bash scripts/backup-db.sh                     # 备份 fssc + fssc_image，保留 14 份
bash scripts/backup-db.sh --keep 30 --dbs fssc
```

- 方式：`mysqldump --single-transaction --routines --triggers --events`，InnoDB 一致性快照，**不锁表**，可在线执行；
- 输出：`backup/<yyyyMMdd-HHmmss>/{fssc,fssc_image}.sql.gz` + `META.txt`（binlog 位点 + 各库表数/近似行数基线）；
- 校验：备份后自动 `gzip -t` 完整性校验，并拒绝小于 1KB 的"空备份"；
- 保留：默认 14 份，超出自动清理最老目录。

**必须加到系统计划任务**（示例：每天 02:00 全备，每周日 03:00 保留 30 份）：

```cron
0 2 * * *   cd /data/fssc && bash scripts/backup-db.sh --keep 14 >> backup/cron.log 2>&1
```

> Windows 计划任务等价配置：`程序= C:\Program Files\Git\bin\bash.exe`，`参数= -lc "cd /d/SourceCode/Ashare/fssc && bash scripts/backup-db.sh"`。

### 3.2 恢复演练（每季度至少一次，并留存记录）

```bash
# 演练：恢复到临时库并自动比对行数，不动生产库
bash scripts/restore-db.sh --dir backup/20260910-195911 --db fssc
```

脚本行为：校验 gzip → 建演练库 `<db>_drill_<时间戳>` → 灌数据 → 对比**表数量**与 7 张关键表（`exp_bill`/`op_voucher`/`op_voucher_line`/`inv_invoice`/`sys_user`/`sys_menu`/`wf_business_flow`）**行数** → 打印 `[恢复演练通过]` 或差异项 → 清理演练库。
加 `--keep-drill` 可保留演练库供人工抽查。

**2026-09-10 演练记录（首次）**

| 项 | 结果 |
|---|---|
| 备份 | `backup/20260910-195911/`，fssc 36MB / fssc_image 4.1KB，gzip 校验通过 |
| 恢复目标 | `fssc_drill_20260910200021` |
| 表数量 | 源 249 → 演练库 **249**，一致 |
| 关键表行数 | `exp_bill` 47·47、`op_voucher` 24·24、`op_voucher_line` 48·48、`inv_invoice` 14·14、`sys_user` 137·137、`sys_menu` 454·454、`wf_business_flow` 78·78，**全部一致** |
| 结论 | **通过**（`[恢复演练通过] 表数量与关键表行数全部一致`） |

### 3.3 时间点恢复（PITR）

`backup/…/META.txt` 记录了备份时刻的 `SHOW MASTER STATUS`（binlog 文件名 + position）。需要恢复到"误操作前一秒"时：

```bash
# ① 先恢复到最近一次全备
bash scripts/restore-db.sh --dir backup/<最近> --db fssc --force-prod
# ② 再用 binlog 重放到目标时刻（示例）
mysqlbinlog --stop-datetime="2026-09-10 20:30:00" \
  /var/lib/mysql/mysql-bin.0000xx | mysql -uroot -p fssc
```

前提：MySQL 必须开启 `log_bin`（**上线前请确认** `SHOW VARIABLES LIKE 'log_bin'` 为 ON），否则没有 PITR 能力。

## 五、尚未闭环的外部依赖（P0-B4 / B5）

以下两项**不是研发工期问题**，须并行推进，否则会成为整体上线瓶颈：

### B4 第三方通道真实对接验收（外部资源依赖）
| 通道 | 当前状态 | 切换到真实实现的方式 | 需要谁 |
|---|---|---|---|
| OCR 发票识别 | 默认 `mock`（确定性模拟票面） | `fssc.ocr.channel=http` + 在「系统设置→全局参数」配置 `ocr.api.url` / `ocr.api.token` / `ocr.api.mapping` | 引擎供应商账号（百度/腾讯/开灵等） |
| 银企直联 | 默认 `DefaultBankGateway`（模拟） | 配置 `fssc.bank.gateway=http` + 银行网关地址与密钥 | 银行方接口权限 |
| 税务/税局接口 | 未联调 | 待接口方提供 | 税局或第三方服务商 |

**验收要求**：每个通道需用**真实凭据**跑通「单笔成功 + 单笔失败（超时/报文错） + 幂等重试」三组用例并留存记录。

### B5 正式 UAT 验收
现状：所有 E2E 均为**研发自测**，无客户方签字记录。
**要求**：按 `docs/19` 第三节的场景 A–K 组织客户方业务人员实操，输出《UAT 验收记录》并取得签字；**没有客户签字的"验收"，交付物不成立**。
